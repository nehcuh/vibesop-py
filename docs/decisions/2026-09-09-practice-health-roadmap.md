# 从实践反思到下一轮开发：VibeSOP 项目体检

日期：2026-09-09。基线：`461c514`，版本 8.2.0。对象：两篇方法论文章、23页原PPT、当前源码、测试、四个平台适配器。本文区分复现的缺陷、已有能力和待验证的产品方向。

## 判断

下一步最有价值的投入，是让经验确实帮助完成任务，并留下可核对的证据。VibeSOP 已有较丰富的技能发现、路由、候选晋升和观测能力；继续增加技能和角色数量，难以回答用户最关心的“少返工了吗”。应先补齐入口与验收的确定性，再用小规模对照实验决定扩展什么。

新论文也改变了我们对技能价值的解释：技能可能补全需求、补充知识，也可能让执行更稳定。“模型本来就知道”不足以推出“技能没有价值”。[论文核验与两文对照](../research/2026-09-09-agent-skills-paper.md)保留了比较对象和实验边界。

## 已有基础

| 能力 | 当前证据 | 应保留的边界 |
|---|---|---|
| 技能元数据统一 | `src/vibesop/spec/models.py` 的 `SkillSpec` | 这里的 spec 是技能格式，不是业务任务书 |
| 明确点名与自动选择分开 | `core/routing/explicit_layer.py`、`matcher_pipeline.py` | 不能只在一个入口实现，生成文件也要一致 |
| 路由回归检查 | `.github/workflows/ci.yml` 的 `routing-benchmark` | 已有硬检查，无需重新发明；基准允许已知失败存在 |
| 候选有人工处置 | `core/observability/skill_promote.py` 的候选状态、编辑指纹；`core/instinct/routing_pending.py` 的待审队列 | 候选、激活、执行结果是不同事件 |
| 可关联的计划和执行轨迹 | `ExecutionPlan`、`ExecutionStep`、trace元数据 | 计划完成标记不等于业务验收通过 |
| 观测数据部分脱敏 | `core/observability/span_writer.py` 调用统一脱敏 | 会话镜像并未因此自动具备同等保护 |

这是一个有工程积累的实践项目，当前主要矛盾是不同入口和不同阶段的语义没有完全对齐。建议沿现有模块收敛，不另建一套“企业智能体平台”。

## 亲证的问题与影响

### P1：验收结果缺失或未知时被当成通过

基线 `src/vibesop/core/orchestration/verifier.py:289` 默认 `status=passed`，未知字符串也回落到 PASSED；`verification_loop.py:103` 同样默认 passed。因此合法JSON但缺状态的输出，避开了“解析异常返回ERROR”的保护。独立评审结果本身也是不可信输入，需要校验。

修复要求：只有明确有效的通过状态才能继续；缺失、未知、类型错误都保留为未完成验收。测试必须走 `VerifierAgent.verify()` 的实际解析路径，同时覆盖不同严格程度，不能只测底层枚举。

### P1：验收要求停止，执行辅助函数仍继续后续步骤

基线 `execute_plan_with_verification()` 计算了 TERMINATE 却没有处理；ESCALATE仅写错误，没有停止；执行异常也继续下一项。主控用真实 `ExecutionPlan` 和 `VerificationResult` 构造两步计划，第一步返回FAILED，仍观察到 `['build', 'publish']` 两次执行，结果字典没有错误。

修复要求：执行失败、重试异常、TERMINATE、ESCALATE均停止该顺序执行流程，保留失败信息；明确通过仍继续。这里亲证的是公开辅助函数这条路径，不声称全部主执行引擎都有同一缺陷。

### P1：结构化分解失败后，不能把字段名改称任务

`core/orchestration/task_decomposer.py` 先尝试JSON，再用过宽的正则解析“冒号两侧”。截断的JSON恰好满足这个形状。需要把“有合法子任务”和“解析失败”分开；无效结构应退回原始请求，不能自信地派出伪任务。

### P1：Pi 扩展把输入作为 shell 命令的一部分

`adapters/templates/pi/extensions/vibesop-route.ts.j2` 的转义先处理引号，再翻倍反斜杠，导致引号保护失效。主控在临时目录用无害 `touch harmless-proof` 复现了输入变成额外 shell 命令，验证后立即删除目录。同类检查也发现 OpenCode 参考模板使用 shell 拼接。两处均应使用 `execFileSync` 直接传递 argv，不再自行拼接 shell 字符串；回归测试须实际运行生成的扩展，确认含引号、换行和命令符的输入仍是完整参数，且没有副作用。

### P2：反馈缺失、失效与失败被混在一起

`core/skills/feedback_loop.py` 对 aware 时间戳与 naive 当前时间相减，异常被吞后 `days_since` 变为空，旧技能的提示失效。应统一时间语义并覆盖已有带时区记录。

`core/feedback.py` 把缺少 `was_correct` 的导入记录默认记为成功，批量导入又只持久化最后一条。缺证据应拒绝或明确排除，不能简单改为“算失败”。本轮主控据此退回 Claude 第一版方案，要求严格布尔校验和完整批量持久化。

### P2：平台生成与评测有遗漏的分支

- 部分重新生成的技能文件丢失 `disable-model-invocation`，使人工点名限制在转换中消失。应覆盖真实生成、再解析的往返过程。
- Pi 把无匹配与命令失败都静默放行，后续规则无法知道路由是否已经运行，可能重复路由。应区分合法无匹配、有效命中与执行/数据错误。
- 路由基准只看两次都失败时，可能漏掉“原本没注入，现在注入错误技能”的退化；历史回放又把已经有路由决定但 `has_match=false` 的矛盾记录算进可挽回空白。应修复计数与退出状态，不能把清洗分母包装成准确率提升。

### P1（下一批优先）：Kimi 配置合并会删除用户已有 hooks

Kimi 路报告后，主控用临时 `config.toml` 独立验证：一条 `command = "echo custom-hook"` 的用户 hook，经过 `KimiCliAdapter._merge_config_with_existing()` 后消失，而普通 model 字段保留。`adapters/kimi_cli.py:207` 的循环按整个 `[[hooks]]` 块删除，并不识别是否属于 VibeSOP。下一批应按明确的 VibeSOP 命令归属替换，保留用户 hook、未知结构与顺序，并验证二次部署幂等。这是已有配置合并缺陷，本轮没有实际部署生成配置；不能把它定为已修复，也不以 P0 夸大。

### P2：业务验收证据尚未成为任务书的稳定合同

`ExecutionStep`已有依赖、输入、结果摘要和通用`verification_result`，但没有统一的验收条件、产物指纹、验收命令及结果出处合同。`vibe plan complete-step`可根据操作者请求标记完成。这是有用的状态记录接口，但不能用它证明“确定性验收系统已完整实现”。

本轮先提供[任务书与验收模板](../templates/agent-task-brief.md)，在现有计划旁增加显式验收清单和结果凭据，再决定是否进入模型字段。不要把现有`vibe spec`改名或悄悄改变其含义。

### P2（后续）：计划日志坏行会让两种查询给出不同答案

主控在临时目录写入真实`ExecutionPlan.to_dict()`记录，再追加一行截断JSON。`list_plans()`仍找到1条计划，`get_plan()`却返回None，因为后者遇到任一坏行就退出。位置为`core/orchestration/plan_tracker.py:95`附近。建议统一逐行容错，另加读改写锁；这批先不改变计划持久化格式。

### P2（后续）：全文会话记录不能直接作为企业默认经验库

`core/conversation_import.py:34`明确仍有secret-redaction待办，正文/思考内容会进入镜像；工具值有部分限制，但不代表文本已清洗。文章“记录一切”的建议应改为“记录经授权且必要的证据”。先明确采集范围、脱敏、保留期限和删除，再谈跨项目积累。这里没有声称发现凭据泄露，也没有读取用户凭据来做演示。

修后再跑同一复杂请求，子任务恢复为有意义的意图；但附加验证步骤仍可能引用当前环境没有文件的技能。前者是此次修复的范围，后者仍需在计划交付前增加技能可用性检查，不能声称这条链路已经完全解决。现场重复运行有模型随机性，确定性回归测试才是修复依据。

## 下一步路径

| 顺序 | 可交付结果 | 验收方法 | 不做什么 |
|---|---|---|---|
| 本轮：先修明确缺陷 | 路由坏结构拒绝、验收不再默认通过、各平台生成合同一致 | 失败用例先复现，修后通过；完整测试、路由基线、Linux容器验证 | 不更换路由架构，不扩大默认技能注入 |
| 第1周：保护配置、串联验收 | Kimi 配置合并保留用户 hook；任务书模板 + 验收凭据 | 验收有明确命令/产物/退出码/时间/版本；失败与未运行不能变成通过 | 不把模型“APPROVE”当机器验收结果 |
| 第2周：经验卡的最小试验 | 少量项目真实坑，写清适用前提、反例、验证和来源 | 无经验、历史过程记录、短检查单、技能包同协议对照 | 不以读了几次技能代替收益 |
| 第3周：路由与使用分开看 | 选中、交付给模型、实际读取、应用、验收五段记录 | 同一run_id关联；缺数据标unknown；分别报告误触发与最终成功 | 不将非标准答案但有效的技能一律判业务失败 |
| 第4周：按结果决定扩展 | 单代理与独立并行任务的比较报告 | 同任务同验收，统计通过率、人工返工、总调用成本和总耗时 | 不预设“小模型一定够用”或“多代理一定更快” |

四周是建议节奏，不是工期承诺。每周只有在上一阶段证据可用时才扩展。暂缓全面自动改技能、自动跨项目激活、大规模常驻专家角色和默认全量记录。

## 最小整机实验草案

目标：检验“明确任务书 + 独立执行 + 确定性验收 + 经验复用”是否降低返工。先挑10个来自真实开发的任务，覆盖修缺陷、增接口、数据处理、文档生成，保留此前未见的同类任务用于迁移检查。10个是工程试点规模，不能冒充统计证明。

分两步进行，避免把所有变量一次改变：

1. **经验的效果**：固定模型、运行环境、任务书、预算和验收，比较无经验、历史过程记录、短检查单、技能包；各任务各条件至少重复3次。每次重置状态，记录技能内容哈希、是否读到、实际产物和验收。旧经验只来自训练/历史任务，不含留出题答案。失败与基础设施错误保留在总分母，另外报告有效运行子集。
2. **分工的效果**：使用相同已定稿任务书，比较单代理执行与独立子任务并行；单独再测不同价格模型。每条件保持验收与总预算一致。并行必须能分开文件/状态，有明确接口，子任务失败不能被上层状态掩盖。

主要指标为任务验收通过率、人工返工分钟数、每个通过任务的总调用成本。延迟、工具次数、读取次数是解释指标。事先约定失败分类、缺失值处理、终止预算和判断标准。LLM评审为补充，确定性结果与人工需求验收各有出处。

[Anthropic 的评测实践](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)将最终环境状态与模型自述分开，并建议用多次运行处理随机性。这与本轮实测验收缺陷直接相关。项目应优先完善这样的区分，而非再增加一层“评审人格”。

## 两文与PPT需要统一的口径

| 原说法 | 建议表述 |
|---|---|
| 题写满，技能归零 | 我们的小样本里没有观察到稳定的额外收益；执行可靠性仍需重复实验 |
| 弱模型仅差1.5分 | R6证明有支撑环境下能产出可评分结果，不能与不同协议的R5作等价比较 |
| R7评委分裂就是答案 | 说明评价存在分歧，不能据此证明零效果 |
| R8表明粗需求更有技能收益 | 人评观察提示这个假设，盲评与单变量复现实验尚欠缺 |
| 图写满就能让普通模型达到强模型水平 | 明确任务书可能降低执行难度，具体模型能否胜任需按任务验证 |
| hook让规则想跳也跳不过 | hook能加强约束，但要验证入口、错误处理和绕行路径 |
| 记录一切 | 记录必要、经授权、可脱敏和可删除的证据 |
| 研究系统约15倍token | 原文基准是聊天，不是单代理；企业试点按通过任务总成本计算 |

成本比较的原始口径见 [Anthropic 多代理研究系统](https://www.anthropic.com/engineering/multi-agent-research-system)。本文不据该研究推算本项目的投入产出。
