## 主控复现

- 有效计划后追加截断 JSON：`get_plan` 返回空，而 `list_plans` 与 trace 查询仍能找到计划。
- 有效计划后追加 `[]`、`null` 或 `17`：三种查询入口均抛 `AttributeError`。
- 给验证步骤预填一个已不存在的技能路径：路径注解方法保留原路径，步骤仍为 pending，没有可用性诊断。
- 上一轮已亲证 Kimi 合并删除用户自定义 hook，本轮以临时配置再次验证修复，不操作用户实际配置。

## 如何使用验收证据

验收记录只说明某个命令在记录的环境和代码状态下实际得到了什么结果。它不能自行证明用户需求完整实现，也不能证明技能、多代理或某个模型提高了效率。

下一个对照试验应保持任务、验收、模型和预算一致；分别记录条件、失败、基础设施错误和缺失数据。成本、人工返工尚未测量时保留未知，不能填零。先使用本轮工具记录真实项目验收，再整理同题多条件的试验协议。

## 最终集成记录

### 实际交付与主控裁决

1. **用户配置保留**：Kimi 初稿改为按明确命令识别自有 hook；主控交叉检查又复现了注释/普通字符串中的三引号误判、跨无关表头的 hook 子表错归属。修正词法状态后，增加完整 TOML 语义核对；不能可靠合并时拒绝写入。用户 hook 的相对顺序保留，生成 hook 追加在末尾。不会实际部署或修改用户的配置。
2. **计划查询与并发更新**：Claude 实现统一的逐行读取与跨进程锁。主控补充非法 UTF-8、无换行断尾、只读挂载锁失败及 Dashboard 同类读取路径；追加记录先分隔未完成尾行，避免新记录被坏尾行吞掉。最后一条有效记录作为当前状态，损坏数据不覆盖先前有效状态。
3. **计划交付前检查**：Grok 首次调用因 `list_dir` 工具错误未产出文件改动；改为提供源码的只读设计分析。主控结合原生实现助手完成 CLI、hook、guide、manifest 四类出口的检查：必需技能缺失、空内容或占位内容时整计划阻断，验收步骤及原因仍保留。同一技能的不同步骤按步骤保存各自来源；已选定文件消失后不会偷偷换成同名副本。未采纳“失效来源直接回退全局搜索”及“删掉坏步骤继续部分执行”的建议。
4. **实际验收凭据**：Pi 提供记录 CLI、测试和文档；主控补充运行前 Git 状态、有限正数超时、原始字节日志、POSIX 进程组终止及产物读取错误。已用该工具记录本轮主机和容器验收，包括首次失败，未删除失败数据。

四条路线均经过实际 Kimi CLI 的独立只读复审，最终结论均为 APPROVE；计划存储增量再次复核。主控以源码、反例和实际执行结果判定是否采纳，APPROVE 本身不是验收凭据。

### 本轮边界与下一步

- 交付前检查不保证文件在交付后不被其他进程改动，也不等同于技能内容安全审查。现有 unsafe 内容拒绝与计划整体可执行状态仍有不一致，需要单独收敛。
- 默认对抗验证器仍引用可选技能；环境未安装时现在会明确阻断，不会自动选出合适替代。下一步应按任务类型定义验证器选择，不能用代码评审技能替代所有领域的验收。
- JSONL 仍是追加式文件，读时扫描全量；大历史量下应先测量锁等待与查询延迟，再考虑压缩。只读无法加锁时为尽力读取，Dashboard 并发追加期间仍可能出现瞬时查不到。
- 配置合并优先保护语义，极端合法 TOML 若无法可靠切块会拒绝合并。紧贴自有 hook 的注释视为该块的一部分，随块替换；既有非 hook 配置继续保留，生成的非 hook 设置不在本次合并范围。
- 记录器只给出机器验收凭据，`condition` 是声明标签；没有自动改变条件、采集模型成本或把计划标为完成。Windows 进程组行为、慢速/benchmark 套件及云端 CI 未在本轮验证。

建议后续依次做：明确验证器选择与内容拒绝状态；选取少量真实任务开展同题对照；将“选中、交付、读取、应用、验收”按同一运行标识关联。先积累结果，再决定是否扩展默认自动化范围。
