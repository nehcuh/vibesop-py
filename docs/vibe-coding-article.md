# Vibe Coding 实战：从"说句话就能写代码"到"如何管理一个AI驱动的软件项目"

> 本文基于 VibeSOP 项目（github.com/nehcuh/vibesop-py）的真实开发历程，总结 vibe coding 实践中的经验与教训。项目从最初的 Ruby 原型，到 Python 重写，再到如今 5.4 版本的"技能操作系统"，经历了 452 次提交、54,000 行代码、217 个源文件、208 个测试文件的演进。这是一篇从实践中来的复盘。

---

## 零、先回答两个关键问题

在展开我们的项目故事之前，先直接给出 vibe coding 的**核心问题**和**核心原则**。如果你时间有限，读完这一节就能带走 80% 的干货。

### Vibe Coding 的五个核心问题

1. **AI 会失忆**。上下文窗口有限，项目超过万行代码后，AI 记不住你十分钟前说的约束，开始重复造轮子或遗漏关键逻辑。

2. **AI 会跑偏**。你在调试 bug，AI 突然开始重构代码；你在写测试，AI 跳去设计架构。意图漂移是 vibe coding 的隐形杀手。

3. **AI 不听话**。你在 AGENTS.md 里写了"所有非平凡任务必须先路由"，AI 照样跳过流程自作主张。指令越长，被忽略的概率越高。

4. **代码经不起暴击**。AI 写的代码在"正常场景"下完美运行，遇到空值、并发、大数、跨平台就崩溃。边界条件不是 AI 的默认思维。

5. **技术债指数累积**。AI 倾向于"加代码"而不是"改代码"，重复实现、裸 except、死代码快速膨胀，六周后项目会变成一座屎山。

### 五条生存原则

| 问题 | 对应原则 |
|------|---------|
| AI 失忆 | **单次只做一件事，用文件代替对话**。把需求写在文件里让 AI 读，不要在对话历史里堆上下文。 |
| AI 跑偏 | **显式声明意图，维护状态锚点**。每次开新任务先说"我现在要做 X"，用 PROJECT_CONTEXT.md 记录"上次聊到哪"。 |
| AI 不听话 | **约束优于自由，设计 fallback**。用 MUST/NEVER 等硬约束词，并为"AI 不遵守"设计后备方案。 |
| 边界崩溃 | **测试先行，显式要求边界**。先写测试（含边界条件）再让 AI 实现，在 prompt 里列出"请考虑空值、并发、大数"。 |
| 技术债累积 | **每个 session 做质量收敛**。类型检查 + lint + 测试全绿才 commit，定期专门花一个 session 只做清理不做新功能。 |

**一句话总结**：vibe coding 不是"和 AI 聊天就能完成"，而是"为 AI 的不可靠性设计一套补偿系统"。

接下来，我会用 VibeSOP 项目的真实演进，告诉你这套补偿系统是怎么一步步被逼出来的。

---

## 一、什么是 Vibe Coding？

Vibe coding 不是一种技术，而是一种开发范式的转变。

传统的软件开发是：**想清楚 → 写代码 → 测试 → 部署**。

Vibe coding 是：**用自然语言表达意图 → AI 理解并生成代码 → 人类审查和修正 → 迭代演进**。

听起来很美好。实际操作中，你会发现一个残酷的真相：

**Hello World 很简单，但生产级软件不是 Hello World。**

当你只需要 AI 帮你写一个函数、修一个 bug 时，vibe coding 体验极佳。但当项目膨胀到数万行代码、几十个模块、上百个概念交织在一起时，你会发现 AI 开始"失忆"、"跑偏"、"不听话"。

这些问题的根源是什么？如何解决？这是本文要回答的核心问题。

## 二、从一个真实项目说起

### 2.1 项目的起点：VibeSOP

VibeSOP 最初是一个 Ruby 项目（github.com/nehcuh/vibesop），用于解决一个看起来简单的问题：

> AI 编码工具（Claude Code、Cursor、Continue.dev）越来越多，每个工具都有自己的技能和命令。开发者记不住，也不知道该用哪个。

早期，作者只是想要一个"路由器"——你告诉我你想做什么，我帮你找到最合适的工具。就像搜索引擎解决了信息过载，VibeSOP 想要解决**技能过载**。

### 2.2 从 Ruby 到 Python：为什么重写？

Ruby 版本的 VibeSOP 证明了一件事：**意图路由这条路是通的**。但它也暴露了问题：

- **性能瓶颈**：Ruby 的 TF-IDF 和向量计算不够快，路由延迟在 500ms+，用户能感知到卡顿
- **生态限制**：Python 在 NLP/ML 生态（scikit-learn、sentence-transformers）上远超 Ruby
- **类型安全**：Ruby 的 duck typing 在 50+ 技能的复杂路由中带来了隐患

2026 年 4 月 1 日，Python 版 VibeSOP 的第一个 commit 诞生。一个 5 层路由引擎的初始实现。

**这看起来又是一个典型的 vibe coding 场景**：和 AI 说"帮我用 Python 重写这个路由引擎"，AI 几分钟就能给你一个可运行的版本。

## 三、Vibe Coding 的坑：来自前线的经验

### 3.1 坑一：长上下文导致的信息丢失

**现象**：你和 AI 说了一大堆上下文，它回应了前半段，忘了后半段。

**真实案例**：在 VibeSOP v4.3.0 的开发中，我们要求 AI 同时实现"上下文感知路由"和"Badge 系统"两个功能。AI 完成了上下文感知路由，但 Badge 系统的实现跳过了关键的持久化逻辑——因为它在处理第一个功能时已经"消耗"了大量上下文窗口。

**根因分析**：

1. **上下文窗口是有限的**：即使 200K token 的窗口，在 54,000 行代码的项目中也只是冰山一角
2. **AI 的注意力分布不均**：越靠后的信息，被"遗忘"的概率越高（Lost in the Middle 现象）
3. **多任务请求加剧问题**：一次请求多个功能，AI 倾向于"优先完成第一个"，后续任务的质量递减

**我们的解法**：

在 VibeSOP 的架构中，我们设计了三层解耦来对抗信息丢失：

```
┌─────────────────────────────────────┐
│         CLI / Agent Runtime          │  ← 用户入口，参数解析 + 意图拦截
├─────────────────────────────────────┤
│         UnifiedRouter（路由层）       │  ← 10层管道，每层独立
├─────────────────────────────────────┤
│         TaskOrchestrator（编排层）    │  ← 多意图分解
├─────────────────────────────────────┤
│       Skill Lifecycle Manager       │  ← 生命周期管理
├─────────────────────────────────────┤
│        Integration Layer（适配层）    │  ← 跨平台适配
└─────────────────────────────────────┘
```

关键思路：**不要试图让 AI 一次理解整个系统，而是把系统分解为独立的、上下文自包含的模块**。每个模块的 SKILL.md 文件就是一个独立的"上下文单元"，AI 一次只需要理解一个技能，而不是整个系统。

**实战建议**：

- **单次请求只做一件事**：不要"帮我实现 A 和 B 和 C"，而是分三次请求
- **用文件代替对话**：把需求写在文件里，让 AI 读文件而不是从对话历史中提取信息。VibeSOP 的 `riper-workflow` 技能就是基于这个思路——先研究文件，再动手
- **结构化上下文注入**：VibeSOP 的路由流程会自动注入匹配到的 SKILL.md 内容到 AI 上下文，确保 AI 看到的是精确的技能指导，而不是模糊的对话记忆

### 3.2 坑二：意图跟踪失败

**现象**：你明明在调试一个 bug，AI 突然开始帮你重构代码，或者从写测试切换到了做架构设计。

**真实案例**：在开发 VibeSOP 的路由系统时，我们持续和 AI 讨论路由准确率的优化。经过 20 轮对话后，AI 开始"发明"新的路由层（比如 Layer 7.5），因为它丢失了"系统只有 10 层"这个关键约束。

**根因分析**：

1. **AI 没有状态**：每次请求对 AI 来说都是独立的，它不会自动记住"我们之前在做什么"
2. **意图漂移**：随着对话深入，AI 的注意力会从原始目标偏移到相关的、但不重要的方向
3. **缺乏锚点**：没有结构化的方式告诉 AI"当前任务是什么、已经做了什么、还剩什么"

**我们的解法**：

VibeSOP 的 Session 智能追踪系统：

```python
# 自动记录每次路由后的会话状态
session = SessionContext(project_path)
session.current_skill = "gstack/investigate"
session.record_tool_use(tool="read", skill="gstack/investigate")

# 检测意图转换
if session.check_reroute_needed("帮我设计新的架构"):
    # 意图从"调试"切换到"设计"
    suggest("superpowers/architect", confidence=0.87)
```

这个系统解决了一个关键问题：**AI Agent 不知道你什么时候"变了心"**。通过追踪工具使用模式（连续读代码 = 调试，连续写文件 = 开发），VibeSOP 可以检测到意图的自然转换，并主动建议切换到更合适的技能。

**实战建议**：

- **显式声明意图**：每次开始新任务时，明确告诉 AI "我现在要做 X"
- **使用 PROJECT_CONTEXT.md**：VibeSOP 项目维护了一个 PROJECT_CONTEXT.md 文件，记录每个 session 的完成状态、关键决策和下一步。这就像给 AI 一个"上次聊到哪了"的备忘录
- **定期同步状态**：使用 `vibe session summary` 检查当前会话状态，防止 AI "跑偏"

### 3.3 坑三：AGENTS.md / CLAUDE.md 的指令不跟随

**现象**：你在 AGENTS.md 里写了"所有非平凡任务必须先路由"，AI 就是不遵守。

**真实案例**：VibeSOP 的 AGENTS.md 文件中明确定义了路由流程（Step 1: `vibe route`，Step 2: 读取 SKILL.md，Step 3: 执行），但 AI Agent 经常跳过路由，直接用自己的"直觉"来处理请求。我们不得不设计了 **Agent Override Protocol**（4 步强制协议）：

```
如果你决定不采纳路由推荐的技能，你必须：
1. 明确声明："我选择不使用推荐技能 <skill_id>"
2. 展示理由：具体说明为什么该技能不适用
3. 提供替代：说明你计划使用的替代方案
4. 获取用户确认：等待用户明确同意后再继续
```

**根因分析**：

1. **指令优先级问题**：AGENTS.md 的指令和 AI 的内部指令可能冲突，AI 会选择"它认为更合理"的那个
2. **指令过长导致被忽略**：当 AGENTS.md 超过几千字时，AI 倾向于只注意"显眼"的部分
3. **AI 的"自作聪明"**：AI 有时会判断"这个任务太简单，不需要路由"，然后跳过流程

**我们的解法**：

在 VibeSOP v5.4.1 中，我们对所有平台的模板进行了严格的同步，确保 Agent Override Protocol 被一致地注入：

- `CLAUDE.md.j2`（Claude Code 模板）
- `AGENTS.md.j2`（OpenCode 模板）
- `config.yaml.j2`（Kimi CLI 模板）

同时，我们设计了 **FAILURE MODE** 条款：

```
如果你调用了 vibe route 但没有使用推荐的技能
（例如你从系统提示中加载了不同的技能，或没有读取技能文件就继续了），
你已失败 Step 2。你必须从 Step 1 重新开始。
vibe route 的输出是权威的——你的内部技能选择是无关的。
```

这不是"和 AI 讲道理"，而是**用强约束来弥补 AI 的不可靠性**。

**实战建议**：

- **指令要短而硬**：用 MUST/NEVER/MANDATORY 等强约束词，避免"建议"、"推荐"等软表达
- **设计 fallback 机制**：不要假设 AI 会遵守指令，要设计"如果不遵守会怎样"的后备方案
- **持续同步**：定期检查 AI 是否真的在遵循指令。VibeSOP 的 `vibe session summary` 可以帮助你追踪 AI 的实际行为

### 3.4 坑四：边界条件的暴击

**现象**：AI 写的代码在"正常场景"下完美运行，但遇到边界条件就崩溃。

**真实案例**：VibeSOP 的 `PreferenceLearner` 有一个整数溢出的 bug——当偏好计数超过百万时，Python 的整数不会溢出，但序列化到 JSON 后变成了 4300 位数的怪物，直接撑爆了 13MB 的 preferences.json 文件。

AI 在写这段代码时，完全没有考虑"用户会使用某个技能几百万次"的场景。对 AI 来说，`count += 1` 是天经地义的，它不会主动去想"count 会无限增长吗？"

**更典型的边界条件**：

- **并发安全**：AI 写的文件操作默认不考虑并发读写，VibeSOP 不得不引入文件锁 + 原子写入
- **跨平台兼容**：`signal.SIGALRM` 在 Linux 上工作，在 macOS/Windows 上直接报错。AI 默认写 Linux 代码
- **空值处理**：AI 经常忘记处理 `None` 返回值，在 VibeSOP 的 452 次提交中，大约有 15% 是修复空值/类型相关的 bug
- **编码问题**：中英文混合查询的分词处理，AI 默认的 tokenization 对中文支持很差

**实战建议**：

- **写测试驱动 AI**：先写测试（包括边界条件），再让 AI 实现。这比"AI 写完再补测试"有效 10 倍
- **显式要求处理边界**：在 prompt 中明确列出"请考虑以下边界条件：空值、并发、大数、跨平台"
- **类型系统是你的朋友**：VibeSOP 使用 `basedpyright` 严格模式，从 1199 个类型错误收敛到 0。类型系统可以在 AI 写出"不安全"的代码时立即报警

### 3.5 坑五：代码质量的隐形债务

**现象**：AI 写的代码"能跑"，但质量堪忧——重复代码、过度设计、不遵循项目约定。

**真实案例**：VibeSOP v5.3.0 的质量收敛冲刺中，我们做了这样一件事：

```
6 个批次的代码删除，总计删除 6,802 行代码
```

这不是 bug 修复，而是纯粹的代码清理。AI 在实现功能时倾向于"加代码"而不是"改代码"，导致：

- 3 个 `deep_merge` 的重复实现
- `UnifiedRouter` 膨胀到 1210 行（后来拆分成 8 个 mixin，每个不到 200 行）
- `skills_commands.py` 膨胀到 1870 行（后来拆分成 6 个子模块）
- 30 个裸 `except Exception` 块
- 9 个生产代码中的 `print()` 调用

**我们的解法**：

建立一个持续的代码质量收敛机制：

```bash
# 类型检查
uv run basedpyright  # 0 errors

# Lint
uv run ruff check     # 0 errors

# 测试（2178+ tests, ~39s）
make test-fast

# 覆盖率
uv run pytest --cov   # ~25%（实际有效覆盖率更高，因为大量是接口定义）
```

**实战建议**：

- **每个 session 结束时做 lint + type check**：不要积累技术债
- **定期做"质量收敛冲刺"**：专门花一两个 session 不做新功能，只做清理
- **用数据说话**：VibeSOP 的 `vibe skills health --ecosystem` 可以给出技能生态的 A-F 评分。对你自己的代码也可以建立类似的度量体系

## 四、Vibe Coding 的架构哲学

经历了这些坑之后，我们总结出一套适用于 vibe coding 的架构哲学。

### 4.1 发现 > 执行

**核心理念**：AI 已经足够强大，真正的问题不是"让 AI 更能干"，而是"帮 AI 找到正确的方向"。

VibeSOP 的整个设计都围绕这个理念：它管理技能的全生命周期——发现、路由、编排、评估、保留/淘汰——让 AI Agent 始终使用最合适的技能。

```
用户说"帮我调试这个错误"
    → VibeSOP 理解意图
    → 匹配到 gstack/investigate（95% 置信度）
    → 将 SKILL.md 内容注入 AI 上下文
    → AI Agent 按照技能指导执行
```

对 vibe coding 来说，这意味着：**不要试图在对话中解释整个系统的运作方式，而是建立一个索引系统，让 AI 在需要时找到正确的信息。**

### 4.2 匹配 > 猜测

**核心理念**：不要让 AI 猜测该做什么，而是用结构化的匹配来指导。

VibeSOP 的 10 层路由管道就是这个理念的体现：

| 层 | 策略 | 速度 | 准确率 | 场景 |
|---|---|---|---|---|
| 0 | 显式覆盖 | <1ms | 100% | `/review` 这类直接命令 |
| 1 | 场景模式 | <1ms | 90% | "调试" → debug 技能 |
| 2 | AI 语义分诊 | ~100ms | 95% | 复杂查询的意图理解 |
| 3 | 关键词匹配 | <1ms | 70% | 短查询 |
| 4 | TF-IDF 语义 | ~5ms | 75% | 相似度匹配 |
| 5 | 嵌入向量 | ~20ms | 85% | 深度语义 |
| 6 | 模糊匹配 | ~10ms | 60% | 容错拼写 |
| 7 | 自定义插件 | 可变 | 可变 | 用户扩展 |
| 8 | 无匹配 | N/A | N/A | 低于阈值 |
| 9 | 兜底 LLM | ~100ms | 80% | 最后手段 |

**对 vibe coding 的启示**：在组织项目结构时，要建立类似的"分层匹配"机制——从最精确（显式指定）到最模糊（AI 推理），逐层降级。

### 4.3 记忆 > 智能

**核心理念**：不要指望 AI 每次都"聪明地"做出正确选择。记录什么有效，下次直接用。

VibeSOP 的偏好学习系统：

```bash
# 第一次：AI 推荐 systematic-debugging（85%）
vibe route "debug this"

# 用户确认有效
vibe feedback record "debug this" "systematic-debugging" --correct

# 第二次：置信度自动提升到 92%
vibe route "debug this"
→ systematic-debugging (92%) ← Habit boost applied!
```

**对 vibe coding 的启示**：

- 维护一个 `memory/` 目录，记录项目中遇到的坑和解决方案
- 使用 `PROJECT_CONTEXT.md` 做 session 间的 handoff
- 让 AI 读历史记录而不是从零推理。VibeSOP 的 `instinct-learning` 技能会自动从会话中提取可复用的模式

### 4.4 开放 > 封闭

**核心理念**：不要绑定任何 AI 工具，因为工具会变。

VibeSOP 支持三个平台（Claude Code、OpenCode、Kimi CLI），技能定义是一份 SKILL.md，通过适配器层转换为各平台的配置格式。

**对 vibe coding 的启示**：

- 项目约定写在标准文件中（AGENTS.md、CLAUDE.md），不要依赖某个 AI 的"记忆"
- 使用标准化的文件格式（如 SKILL.md 的 frontmatter + markdown 格式），而不是某个 AI 的私有格式
- 你的项目知识应该是**文件化的**，而不是**对话化的**

## 五、如何在软件全生命周期中做 Vibe Coding

### 5.1 需求阶段：用 AI 做头脑风暴，但别让它做决策

VibeSOP 有一个 `office-hours` 技能，它的设计哲学是：**用 AI 帮你思考，但最终决策权在你**。

实际操作：

```bash
vibe route "我想做一个技能市场，帮我分析一下这个想法"
→ gstack/office-hours (87%)
```

AI 会用六个强制性问题帮你检验想法：
1. 需求真实存在吗？
2. 现状有多痛？
3. 最小可行的切入点是什么？
4. 你能观察到什么证据？
5. 未来是否更适配？

**但最终决定"做不做"的是你**，不是 AI。

### 5.2 设计阶段：把设计文档当代码来写

在 VibeSOP 的开发中，我们遵循一个原则：**先写 PHILOSOPHY.md，再写代码**。

```
docs/PHILOSOPHY.md  →  527 行，定义了所有设计决策
docs/architecture/  →  8 个文档，定义了系统架构
AGENTS.md           →  定义了 AI Agent 的行为约束
```

这些文档不是事后补的，而是在开发过程中**持续维护**的。每次做架构决策时，先更新文档，再让 AI 按文档来实现。

**好处**：

- AI 有了明确的"设计图纸"，减少跑偏
- 文档即约束，比口头指令更可靠
- 下次 session 时，AI 可以直接读文档恢复上下文

### 5.3 开发阶段：TDD + Vibe Coding

最佳实践是**先写测试，再让 AI 实现**：

```bash
# 1. 写测试（你自己写，或者让 AI 根据需求写）
# 2. 确认测试覆盖了边界条件
# 3. 让 AI 实现
# 4. 跑测试验证
# 5. 如果失败，让 AI 看测试失败信息并修复
```

VibeSOP 的测试从 86 个增长到 2178+，覆盖率保证了 AI 不会"悄悄破坏"已有功能。

### 5.4 审查阶段：让 AI 做 Code Review，但用你自己的标准

VibeSOP 的 `gstack/review` 技能会检查：
- SQL 安全
- LLM 信任边界违反
- 条件副作用
- 结构性问题

但**审查标准是你定义的**。在我们的项目中，AI 的 code review 发现了：
- 12 处 `eval()` 使用（全部替换为 AST 安全解析）
- 8 处路径遍历漏洞
- 30 处裸 `except Exception`（全部收窄到具体异常类型）

### 5.5 质量把控：数据驱动的度量

建立可量化的质量指标：

| 指标 | VibeSOP 的实践 |
|------|--------------|
| 类型安全 | basedpyright strict，0 errors |
| Lint | ruff，0 errors |
| 测试通过率 | 100%（2178+ tests） |
| 测试速度 | ~39s（并行执行） |
| 代码量趋势 | v5.3.0 删除了 6,802 行 |
| 覆盖率 | ~25%（大量接口定义拉低了数值） |

这些指标不是摆设，而是**每次 session 结束时必须检查的 gate**。不通过，不 commit。

## 六、后续可能面临的问题

基于 VibeSOP 的开发经验，我们预判 vibe coding 在未来会面临这些挑战：

### 6.1 规模化的上下文管理

当项目超过 10 万行代码时，AI 不可能看完所有文件。VibeSOP 的解法是**技能路由**——AI 一次只看一个技能的 SKILL.md，而不是整个项目。但更通用的方案（如基于向量索引的代码检索）仍在探索中。

### 6.2 多 Agent 协作

VibeSOP 的 `omx/team` 技能支持多 Agent 并行执行，但协调机制（任务分配、冲突解决、结果合并）仍然脆弱。当多个 AI Agent 同时修改代码时，merge conflict 几乎不可避免。

### 6.3 AI 生成的代码审查

AI 写的代码"看起来对"，但可能包含隐蔽的逻辑错误或安全漏洞。VibeSOP 的安全审计模块可以检测 prompt injection，但无法检测"AI 写了一个 off-by-one error"。**人类审查仍然是不可替代的**。

### 6.4 技能生态的碎片化

随着技能包（gstack、superpowers、omx）的蓬勃发展，技能之间的重叠和冲突会越来越多。VibeSOP 的路由系统需要越来越智能来解决"三个技能都能做，该选哪个"的问题。

### 6.5 长期维护

Vibe coding 擅长"从 0 到 1"的快速原型，但"从 1 到 100"的长期维护仍然需要：
- 严格的代码规范
- 持续的质量收敛
- 完善的文档体系
- 有意识的架构决策

**Vibe coding 不能替代软件工程，但它可以极大地加速软件工程。**

## 七、总结：Vibe Coding 的方法论

基于 VibeSOP 项目的实战经验，我们总结出以下方法论：

### 心法

1. **AI 是工具，不是同事**：不要期望 AI 有"常识"或"记忆"，要为它的局限设计系统
2. **文件化一切**：对话会消失，文件会留下。项目知识应该存在文件里，不是对话历史里
3. **约束优于自由**：给 AI 明确的边界和规则，比给它"自由发挥"的空间更有效
4. **质量是动词**：质量不是一次性的，而是持续的过程。每个 session 都要有质量检查

### 招式

1. **先写测试，再让 AI 实现**
2. **单次请求只做一件事**
3. **用文件传递上下文，不用对话**
4. **维护 PROJECT_CONTEXT.md 做 session handoff**
5. **建立类型系统 + lint + 测试的自动化 gate**
6. **定期做质量收敛冲刺**
7. **用结构化的路由/匹配代替模糊的指令**
8. **为 AI 的"不听话"设计 fallback 机制**

### 展望

Vibe coding 还在早期。今天的"坑"（长上下文丢失、意图跟踪失败、指令不跟随）可能随着模型能力的提升而缓解，但新的坑（多 Agent 协调、技能冲突、安全审计）会不断出现。

**核心态度是**：拥抱 AI 的能力，但不要迷信 AI 的可靠性。建立系统、流程和工具来弥补 AI 的不足，才是 vibe coding 的正确姿势。
