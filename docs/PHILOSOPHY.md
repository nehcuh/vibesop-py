# VibeSOP 工程原则

> 更新：2026-09-14。适用于当前源码开发线；[版本与状态](PROJECT_STATUS.md)单独维护。

## 使命

**让 AI 辅助开发中的选择、执行与结论有可检查的依据。**

VibeSOP 从技能管理工具发展为工程工具与实证研究项目。技能选择仍然重要，但任务是否明确、执行环境如何约束行为、结果如何验收、经验如何被重新使用，同样影响最终交付。完整定位见 [POSITIONING.md](POSITIONING.md)。

## 从明确要求开始

任务需要说明目标、边界、输入输出与验收方法。长文档不等于语义明确；重要接口有歧义时，应把歧义记录出来，而不是用隐藏评测替用户作出唯一选择。

规格和 harness 的作用需要在具体任务上验证。“强模型规划、弱模型实施”等分工属于值得测试的工程假设，不是本项目已经证明普遍有效的流水线。

## 技能按需选择

技能是可查阅的方法与知识。明确匹配时使用，找不到合适技能时允许 no-match。安装量、注入量、匹配率或角色人数都不能替代任务质量。

SkillOS 继续负责发现、安装、作用域、路由、评估和保留/淘汰；它是整个项目的一部分。跨平台复用尊重宿主的配置、工具与权限边界，不承诺“一套配置即所有平台行为相同”。

## 完成以执行证据为依据

计划、模型解释、评审意见、实际执行和验收结论是不同的记录。

- 缺证据、执行失败和验收通过分别记录，不把 unknown 当 false，也不把缺失当成功。
- 验收围绕原始要求与实际产物，保留日志、退出码、版本和必要的产物指纹。
- 模型评审帮助发现问题，意见数量与共识不独自承担放行权。
- 技能不可用或未通过交付检查时，计划保持 blocked，不伪装成可执行计划。

对应实现契约见[验证器与计划交付](architecture/verification-contract.md)和[机器验收凭据](architecture/acceptance-evidence.md)。

## 观测服务于检验

trace、回放与反馈用于回答“实际发生了什么”。有记录之后才能判断某个技能是否被读取、某个角色是否参与、失败发生在模型能力还是执行环境。

调用次数、耗时和输入 token 都有各自口径；输入 token 不直接等同于费用，超时不直接等同于模型能力失败。指标需要版本、分母和采集条件。

## 记忆需要证明效用

检索到旧任务与成功复用旧经验之间还有距离。聚类、recall 与跨项目 pool 是已实现的机制；“越用越准”是需要测量的结果。

保留出处、适用条件与失败记录，对修改建议和技能升级作明确决策。数据增长、自动聚类或定时运行不等于系统已经学会改进自己。

## 用研究约束产品承诺

对照实验保留冻结协议、运行代码、分配记录、失败、中断和原始结果。后续修订与旧结果分别记录；中间发现写明日期和未完成范围。

研究结论只适用于其任务、模型、预算和测量条件。增加技能、多代理或评审轮次是否值得，交给证据判断；不以某一次实验断言所有方法都有效或都无效。

研究入口：[综述](research/research-survey.md)、[实验登记册](experiments/README.md)。

## 执行有明确边界

hook 路径将上下文交给宿主代理。Runtime、loop、prompt-chain 验证和命令记录工具有各自显式配置的执行能力，不能用“VibeSOP 不运行任何命令”概括。

持续任务应有明确目标、失败处理与停止条件；合并、发布及外部副作用遵循实际授权。项目提供工程组件，不替代所有编码代理，也不承诺通用无人开发。

## 开放、可追溯、可恢复

使用开放的技能格式与平台适配，尊重外部技能作者、许可及原文。产品能力以源码和合同为准，研究结论以证据为准，发行状态以实际发布为准。

研究中间材料按主题归档，当前文档有唯一入口。移除 worktree 前保存提交与未提交成果并验证恢复；归档文件存在不等于已经做好异地备份。具体约定见[维护与恢复](maintenance/README.md)。
