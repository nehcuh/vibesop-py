## Pack build: full installer chain, real Docker

Probe: `/tmp/vibesop-pack-functional-repro.py` uses an ordinary legitimate skill plus `BUILD.sh` with `set -e; mkdir -p generated; printf generated > generated/output.txt`. Only RepoAnalyzer.analyze/git_clone are stubbed to a local fixture; real planner, checksum, pre-auditor, post auditor, Docker runtime, build executor, message formatter, project-scoped install, and pack-lock writer run. PackLockStore location, central storage and project root are temporary. No platform symlink/home changes. Docker uses existing ubuntu:22.04 on native linux/aarch64.

Actual output:

```json
{"install_success": true,
 "message": "Installed normal-fixture-pack ...; Skills found: 1; Pre-audit (2 files): 2 file(s) scanned, no critical/high threats; Audit: ordinary-helper: PASS; Build: BUILD.sh blocked/failed in sandbox: mkdir: cannot create directory 'generated': Read-only file system",
 "build_output_persisted": false,

 "lock_written": true}
```

PS-05 confirmed. A valid write-producing build cannot finish because `/work` is read-only (`pack_installer.py:469`), and required build failure is represented as an informational string (`:495`) rather than install failure. `install_pack` continues to lock/publish a pre-build snapshot and returns True (`:220-270`). This is not a claim that any pre-existing markdown skill is unusable: a pack with ready-to-use SKILL.md can remain partially usable. The violated contract is that discovered build scripts run successfully and generated outputs become available, with truthful completion status. Severity P2 unless a release/deployment depends on required generated output, when it becomes a concrete release blocker.

Recommended repair: writable isolated work copy, keep network/resource controls, validate generated outputs, copy allowed build outputs back atomically, and return typed build outcome (not a string-only status) so install can distinguish optional skipped builds, required failure, and complete success. Add clean Docker functional contract test of a legitimate generator, both happy path and shell nonzero, asserting installed artifact content and installer status.

## RR-04 independent confirmation: dynamic failure has contradictory caller state


`step_runner.py:384-394` hardcodes failed/skipped to zero and does not sync engine-updated statuses into `_states`. Add same exception/sentinel outcome contracts across serial, parallel, dynamic and squad.

## Priorities and inference boundary

The repeatable pattern is distinct execution branches interpreting output differently: duplicated status logic leads to contradictory records. One common typed StepOutcome (success/failed/blocked/skipped), one terminal aggregation and explicit build outcome should come before adding more patterns or lanes. Repair RR-03/04/05 as a single-contract family with atomic tests for each ingress. PS-05 can be a separate installer batch.
