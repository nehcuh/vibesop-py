### CC-03 [P2, 高置信] recall 缺 skill_id 确实破坏 replay 的消费者行为

真实链：Span → SpanWriter.write_span → query_recent → should_replay → CLI `_maybe_prompt_replay` → route 所需的 skill 返回值。

- producer `core/observability/span_writer.py:111-134` 对 input/output/metadata JSON 编码为字符串。Span model `models.py:99-125` 无 top-level skill_id。
- `core/observability/recall.py:400-410` 仅从 dict metadata/output 读取，故真实磁盘格式解析不出来。与 query extractor 支持 JSON string 的行为不同。

- should_replay 实际得到 should_prompt=True、is_gold=True、skill_id=None；把这些真实磁盘记录通过真实 should_replay 接入 `_maybe_prompt_replay`，模拟交互确认 Y 后，returned=None、prompt含unknown、真实 learner success_count 仍3（未新增 outcome）。
- 为隔离 IO 的 stub：SpanWriter/InstinctLearner 的构造指向真实临时实例、TTY=True、typer.confirm=True、provenance emit stub；**没有 mock recall result、should_replay 输出、gold 判定或 consumer逻辑**。should_replay side-effect 仍调用真实函数，仅注入固定 cache。

## Narrowed

- CC-01 已证实“安装外部提供的 skill 时，攻击者控制的 frontmatter可以使安装写到root之外”。没有证实远程无需安装动作即可写任意文件。现存目标目录且无force时当前代码只报 already installed；本反例选择不存在的越界目录，无需force即可写。覆盖既有文件要 `--force` 或相关目录/文件路径状态，不能夸大为默认无条件覆盖全HOME。
- CC-02 已证实秘密**意外落盘**，没有证实秘密已上传、被Git提交、被OpenCode发送到第三方。0644是本机默认umask的实际结果；使用077的环境可得到更严格权限，但不能否定密钥被写入构建产物。环境变量中有密钥证明进程有访问权，不等于用户选择了将其持久化/导出。
- CC-03 不会阻止一般 route，且 `--json` / `--minimal` / `--no-replay` / 非TTY主动不走prompt；仅影响互动 gold replay 偏好闭环。skill_id丢失不影响 task query 的相似度检索和trace provenance展示，不应升级为“整个memory系统全坏”。

## Refuted / 未支持

- “installer缺陷只存在于私有helper，公开CLI安全审计必定拦住”：已被真实注册CLI的反例反驳。
- “普通opencode build只有用户显式选择存储密钥才写出实际值”：无该opt-in，真实CLI的反例反驳。
- “recall skill_id缺失仅影响显示，不影响真实消费者”：真实consumer confirmed-return=None与route条件证明不成立。
- 未支持更强断言：任意远程无交互攻击、真实密钥外传、未确认自动回放。不能因当前审计使用哑密钥和模拟确认，把这些风险写成已发生事件。

## Integration 综合判断

跨lane共同问题是边界合同缺少生产形状/完整路径验证：来源 audit不约束目标path；组件生成成功不等于产物不携带秘密；内存dict测试不保证磁盘JSON string roundtrip；workflow verdict不自动进入其他bridge的terminal判定。修复应以公开CLI或真实writer产生输入，再对实际产物和consumer状态验收。不要只在被审组件接口mock相邻层，然后由绿测试推出全路径安全/正确。

## Addendum：真实 DeepSeek E2E T4 的判定

读取 `/tmp/vibesop-audit-20261009/evidence/deepseek-e2e.log` 与 `scripts/e2e_llm_routing.py`，没有再访问 API。

**结论：目前代码语义下 0.88→0.616→62% 被接受是正常；T4 的无条件 scenario_fallback oracle 不稳定。**

- `scripts/e2e_llm_routing.py:318-332` 从某次返回0.82假设衰减后0.57低于min=.6，从而无条件要求scenario_fallback。
- 真实实现 `triage_service.py:920-923` 是 confidence×.7；`unified.py:761` 仅做 `match.confidence >= min_confidence`，不看 last_good。当前项目 `.vibe/config.toml:5` min=.6；边界 original>=.6/.7≈.85714 时 stale照样合格。
- `_last_good_route:905-911` 文档说“confidence may fall below ... rejected”，这支持条件性拒绝；紧接着“stale result should not auto-execute”是比代码更强的语言。`degradation.py:39-40` ≥默认.6 被判AUTO，metadata保留last_good但没有强制执行门禁。路由返回/注入本身仍不等于危险外部动作已执行。
- 独立本地实际 `_last_good_route` 和 DegradationManager：.82→.574(reject，suggest)；.88→.616(accept，auto)；.90→.63(accept，auto)；1→.7(accept，auto)。不依赖新模型调用、不是只手算。
- script有“last-good fired”与最终层的证据，但还应检查payload.meta.last_good、last_good_original_confidence及其衰减计算，而不是匹配某个skill字符串便声称last-good成功。

建议将 real-LLM E2E 的expected outcome基于**实际缓存confidence/当前threshold**计算，或把失效测试拆为固定cache confidence .82与.88两个 deterministic case。若产品希望所有stale只提示不可自动注入，则应把它写成明确hard contract并实现last_good专属门禁；靠.7乘数不保证这一点。

分类：**P2 验证脚本/文档契约歧义**，没有足够证据称新P1安全漏洞。不能把6/7报告改成全绿，也不能由这个oracle失败说last-good degradation机制本身坏了。T1/T2真实模型/cache证据有效，T4需要报告“decay工作，期望终层的断言不适用于本次实际confidence”。
