# 校准执行器与正式协议的一致性审查

在首批校准结果出现之前记录，避免按输赢改变判据。

已具备：五组固定流程、三类校准任务、相同模型与总输出上限、随机分配顺序、SDK 无自动重试、逐调用输入输出与实际 token、隐藏验收和运行隔离、正确/错误实现检验。

正式阶段前仍需补齐：

1. **可见工具回路**：当前模型一次交付文件，没有运行可见测试再修复的能力。正式执行器应提供相同的文件读写与 Docker 命令白名单工具，记录调用，并计入 K；隐藏测试仍只在最终交付后执行。
2. **阶段身份与上下文**：B 应保持完整 assistant/user 历史；C/D 每名成员保持各自历史而非仅拼接摘要，D 的身份贯穿全阶段；避免上下文压缩差异成为额外处理因素。
3. **预算规则**：当前是统一12000上限和阶段上限，E 阶段申请额之和可能超过总额（最终由全局限额截断），正式应直接落实20/50/30和未用额度向后转移。A 应允许使用全额，而不受一次最多6000限制；当前是校准调用限制，不是等可用预算主实验。
4. **任务拆分与权限**：E 当前工人产物是文本建议，由整合者落盘；正式应落实文件所有权和依赖图，并保留冲突/越界证据。
5. **规格变体与澄清**：校准只有完整spec，正式简略spec须有共同问答接口与独立冻结标准，不能人为不给单体信息。
6. **样本冻结与费用**：12个正式任务尚未制作和验证，不复用校准任务作为正式独立样本；冻结服务模型标识并说明别名限制。费用需用实际用量和可核验的费率/账单计算，不能从token上限直接声称成本相等。

因此本批可以诊断结构化交付、截断和验收，但不能发布五组胜负结论。先确认校准结果，再按这些明确条目完善，不能将该审查当作另起一轮挑选赢家的理由。
