# 多专家体系的端到端验证方案

状态：**执行已结算（2026-09-13）**。下文仍是原始设计。实际与设计的差异见文末「执行后状态」，以及 [正式报告](multi-expert-formal/REPORT.md)。本方案不代表项目已证明多专家有效或无效，也不启用产品默认编排。

**不可改**：冻结的 `multi-expert-formal/preregistration.md` 与 harness 源码。本文件只更新非冻结状态。

## 要回答什么

核心问题：相同任务、工具与总资源上限下，多专家委员会能否比单模型交付更多可用产物？其次区分收益来自角色身份、独立尝试、清晰分工，还是额外计算量。

预期方向（待检验）：委员会在边界明确的任务上收益有限；共享状态越多，协调失败越多；明确分工可能在可隔离任务上获益。允许结果推翻这些预期。

端到端指从收到需求，到实现、集成、提交最终产物，再由外部验收器从干净环境执行。不能用方案文采、报告条数或模型自评代替交付结果。

## 五个实验组

主实验全部使用同一模型快照、相同推理设置与工具权限，避免把模型差别误认作组织收益。

| 组别 | 固定流程 | 关键比较 |
|---|---|---|
| A 单体 | 一个 agent 完成理解、实现、自查与交付，可在总预算内迭代 | 实际使用基线 |
| B 单体分阶段 | 同一个 agent 按规划、实现、检查三个阶段工作，保留上下文 | B−A：流程约束的收益 |
| C 无角色委员会 | 三个独立上下文先各自分析，再交换意见一轮；固定其中一名整合、实现、自查与交付 | C−B：多上下文与协商的组合收益，不能单独归因于“人数” |
| D 专家委员会 | 与 C 完全相同；唯一变化是分别赋予架构、实现、质量专家身份及关注面 | D−C：角色与关注面提示的增量；D−A：体系整体价值 |
| E 明确任务分工 | 主 agent 定义接口与验收，两个执行者承担子任务，主 agent 集成并交付；按依赖串行或并行 | E−D：两种实际组织方案；E−A：派工整体价值 |

C、D 的整合者都是三名成员之一，不额外增加第四名模型。双方传递相同格式、相同长度上限的报告；禁止 D 私下获得更好的技能、工具或项目资料。D−C 同时改变身份与关注面，若出现收益，再增加“无专家头衔但相同检查清单”组，进一步判断是清单还是身份的作用。

E 的任务拆解成本必须计入。所有组获得同一份外部输入；不能先由人给 E 写好子任务，再让 A 自行摸索。

## 场景：复用项目失败机制，重新出题

正式任务从三个层次取样，每类至少四个不同任务，共十二个任务。它们是拟构造的任务，不冒充既有实验产物；旧问题已修复时，不在当前代码上假装重现，使用冻结历史基线或专门的小型夹具。

| 场景 | 对应项目经验 | 端到端验收示例 |
|---|---|---|
| 局部、规则明确 | 路由误注入、no-match 语义 | 从真实 CLI 输入语句到 JSON 输出；验证真实收工意图、工人下班叙述、禁止自动注入的技能与不匹配路径 |
| 跨层、接口耦合 | 模板猜技能路径、适配器通过而产品入口失败 | 在干净临时 HOME 生成配置，调用真实入口，确认返回路径可读取、参数传递一致、错误契约完整；不只测试内部 helper |
| 可拆分但需集成 | 量化任务中的时间语义与撮合边界 | 从固定行情与信号输入生成成交记录及汇总；验证不使用未来信息、无下一根行情、费用与输出的一致性 |

每个任务制作两份需求：完整 spec 与简略需求。两者目标和隐藏验收一致；简略版缺省的业务选择可通过固定问答接口查询，所有组获得同一回答，查询成本计入。不能用事先无法获知的任意业务偏好处罚简略组；明确区分通用正确性要求与需要澄清的选择。正式作者不得接触实验产物后修改标准。

由未参与运行的维护者预先准备验收器，包含正常路径、边界、回归与真实入口；设置已知正确实现和至少一个故意错误实现，确认验收器确实能区分。运行环境不向 agent 暴露隐藏测试、期望答案或其他组产物。

## 预算与运行纪律

- 先用不进入正式分析的三个校准任务，确定每种任务统一的总生成 token 上限 T、输入 token 上限 I、工具调用上限 K，以及仅用于防挂起的时间上限。将具体数值写入冻结清单后才能正式运行。不存在“每个专家各给单体一份预算”。
- 所有模型调用均计费计量，包括规划、摘要、读同伴报告、协调、验收失败后的修复；记录缓存命中和真实账单。各组共享同样总上限，但不强迫耗尽预算。单体可以使用全部额度。
- C、D 采用相同预算分配：三份独立分析各最多 10% T，一轮交流总计最多 10% T，整合、实现、自查最多 60% T。未用额度转给整合者；不得增加协商轮次。B 使用同样总额度但无专家间交流。
- E 的规划最多 20% T，两个执行者合计最多 50% T，集成与修复最多 30% T；未用额度可向后转移。所有输入预算与工具上限同时生效。
- 每次运行都从相同提交及依赖锁、全新工作目录和隔离记忆启动；不读取既有实验报告。共同开发过程中的测试可见，最终隐藏验收只在交付后运行，不反馈给模型。
- 预算耗尽、模型运行失败、未交付、改坏入口均保留为结果；不挑最佳尝试。只有经日志证实、符合事先定义的外部基础设施故障可补跑，同时保留原日志与补跑原因。不能把模型导致的 OOM 自动豁免。
- 随机化各组执行顺序并按任务、spec、重复轮次配对；记录模型版本、服务时间段、采样设置、系统提示和工具版本。温度为零也需要重复，不能假定确定性。

固定 token 额度不代表实际货币成本完全相同。主比较是相同资源上限下的成功率，并同时报告实际费用；有明显收益后，再以独立任务验证预算敏感性，不能事后给输家追加资源后仍宣称同预算获胜。

## 什么叫成功

主指标：一次运行在总预算内交付，全部预注册硬性验收通过，且没有越界改动，记为成功；任一不满足记为失败。分母包括全部正式分配的运行。

辅助指标：隐藏检查通过率、回归失败、接口不一致、集成失败、实际费用、输入与输出 token、协调调用占比、人工干预次数。过程原因可以多选，不强行归成单一根因。耗时仅作运行诊断，不据此做墙钟性能宣传。

可维护性作为次要指标，由看不到模型和组别的人工评审按固定量表判断，并保留分歧。LLM 可以提候选问题，但不能作为最终放行闸。“专家发现更多问题”“最终报告更长”都不是成功指标。

## 样本与判定

第一阶段：三个非正式校准任务 × 五组 × 一轮，合计十五次，用来调试协议与验收器，不估计收益。

第二阶段：十二个新任务 × 两种 spec × 五组 × 三轮，合计三百六十次，是初步估计而非预先保证统计功效的最终规模。费用估算在校准后按实测单次费用给出；不能把三轮当成三个独立任务。

预注册主比较 D−A；D−C、E−A、E−D 及与 spec、任务类别的交互作为次要探索。报告每个任务的原始结果、配对成功率差，以及按基础任务聚类的 95% 区间；两种 spec 和重复轮次不拆成独立样本。十二个任务区间可能较宽，不能以不显著宣称等价。

建议将值得采用的最小收益设为成功率提高 10 个百分点（工程决策阈值，非已知事实）。主比较区间下界超过 +10 个百分点，才认为足以支持在受测分布上采用；区间上界低于 +10，只说明不支持达到该工程收益；上界低于 0 才有整体更差的证据。区间跨越这些界限则结论未定。即使成功率提高，也须展示费用与失败严重性，不能掩盖代价。

若初步结果需确认，依据校准/初步方差另做功效设计，使用新任务进行一次固定规模确认实验；不边看结果边加样本直到显著。次要比较若要升级为确认性结论，需预注册多重比较处理和独立验证。

## 如何接上强模型规划、弱模型执行

先完成同模型组织对照。第二个独立实验再比较：强模型单体、弱模型单体、强规划＋弱执行、强规划＋强执行。每组沿用相同任务输入与总资源/费用核算；规划、澄清和集成全部计入，防止把强模型前置工作藏掉。

该扩展回答“能否用清晰分工降低执行成本”，不能混进主实验后解释成“专家角色有效”。与路线图 E4 对齐，进入整机实验前先结算 R8 盲评及运行账本。

## 可复核产物与启动条件

每次保存 run_id、task_id、spec_variant、arm、repeat、base_commit、模型快照、提示/输入哈希、预算和实际用量、最终 diff、完整工具轨迹、可见测试日志、隐藏验收结果、退出原因。保存所有分配记录，包括没有产物的失败。

启动前须完成：R8 结算（涉及 E4 时）、任务与问答包、真实入口验收器、正确/错误夹具校验、五组提示、资源限额执行器、日志脱敏与隔离检查、校准报告、冻结清单。当前只有协议，以上准备未宣称已完成。

论文式报告最终按“预测—实际—失败机制—适用边界”写作。若委员会获胜，修改文章原来的负面评价；若只在可拆分任务获胜，把建议限定到该场景；若结果未定，如实写未定。
