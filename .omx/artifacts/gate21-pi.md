## Findings

**NIT-1 — skill_commands.py:1498-1499:CLI 池统计双重无锁读,数字可能不自洽**
`store.pending_count()` 调两次(一次 `include_unstable=True`、一次默认),每次都是整文件无锁读。两次读取之间若并发 scan 写文件,打印的 `total - stable` 会是不自洽快照(理论上可瞬时为负)。纯展示层。建议单次 `_read_all_unlocked()` 内部分类计数,或接受展示层的轻微竞态并在注释说明。

**NIT-2 — skill_promote.py 准入 cap 不作用于存量池(升级路径展示口径)**
实证:空 store 重建 50 条 unstable 行,第 21~50 条被逐条 refuse(span_count 并列 → `<=` 拒绝),自限到 20 ✅。但**已存在**的 pre-F-a 池文件(如 dogfood 的 50 行)加载时不做裁剪——cap 只拦新插入,存量 50 行会一直停留,CLI 打印 `50 unstable (cap 20)`,诚实但吓人。逐次 evict/TTL(30d)才缓慢下泄。建议:加载后一次性 trim 到 cap,或加一行 "pre-F-a pool 超出 unstable cap,将随 TTL/evict 下泄" 说明。

**NIT-3 — `_do_locked_upsert` 刷新路径可瞬时超 unstable cap**
实证:20 unstable + 50 stable,rescan 把 s0 刷新翻转 stable→unstable 后,unstable=21 > cap 20。existing-row 分支绕过 cap 检查(刷新整行替换,含 is_unstable)。下一次新 unstable 插入时(21 ≥ 20)进入 cap 逻辑自愈,总量守恒、越界 ≤1。属软 cap 语义,建议注释明示或接受。

**NIT-4 — gold 路径 stable 拒绝无显式计数,与 unstable_refused_count 不对称**
`unstable_refused_count` 有显式计数器,但 gold 路径 stable 行被 cap 拒绝时,summary 里只有 `promoted_count`(发计数)与池占用的隐式差异 + store WARNING 日志——`miss_rejected_count` 只覆盖 miss 行。注释已承认("implied by promoted_count vs pool occupancy"),但操作员从 scan 输出无法区分「promoted 5」里 2 条被拒。建议对称加 `stable_refused_count`。

**NIT-5 — clustering.py:368 信封+block 双重包裹时不解二遍,同载荷聚类口径不一致**
`<user_query>[{"type":"text","text":"inner"}]</user_query>` → envelope 解出原始 JSON,block 拆解不重跑(测试锁定该行为)。但 `unified.py:121` 证实平台 hook 仍会包 envelope,kimi/grok 的序列化数组载荷若落在 envelope 内,与裸数组的同文查询将无法合并、卡片依旧不可读——同一载荷因外层信封有无而分道。建议:envelope 内容再做一次**有界单次** block 拆解(不递归),或至少在注释中说明该 shape 的已知不一致。

## Residual risks

1. **M2 出口可复堵**:miss 行(gold_rate=0.0)在 **stable 类** cap 时仍恒输 admit-only-if-better(池内 min ≥ 0.60)。F-a 只解了「unstable 填满」场景——一旦真实 stable 池被 gold 行填满,miss 准入再次被堵,只能靠 promote/dismiss 腾位。这是「miss 行稳定可见」设计的固有属性,非缺陷,但出口的持续可达性依赖人工处理节奏。
2. **F-b 误判面**:整串恰为 `[{"type":"text","text":...}]` 的人为粘贴会被解包(该 shape 与 dogfood 载荷不可区分);`[1,2,3]`/`["a","b"]`/内嵌/畸形均原样放行。误判面收得很窄,可接受。
3. **空 text 块**:`[{"type":"text","text":""}]` 解包为 `""` → `cluster_queries` 的 `if query:` 直接丢弃(良性);miss 池路径喂 `""` 进 `_is_low_information_query`,与改动前空 query 行为一致,非回归。
4. **unstable 驱逐键与审阅排序分叉**:驱逐按 span_count,`list_unstable` 按 gold_rate asc(最病理在最上)——审阅 UI 眼中的"最弱"不是被驱逐的那个。已注释的设计取舍,非缺陷。
