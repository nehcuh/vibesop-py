## Findings

### NIT-1 — legacy 候选的拒绝文案给出了一条走不通的补救路径
`src/vibesop/cli/commands/skill_commands.py:1918-1926`

legacy（`draft_sha256 is None`）分支文案建议："Re-run `vibe skill promote` once to record the hash, edit the draft, then activate"。但按 `promote_cmd` 的逻辑（`:1828-1829`）：

```python
draft_path = drafts_root / skill_id / "SKILL.md"
fresh_write = not draft_path.exists()   # legacy 候选的草稿已存在 → False
```

legacy 候选（M5 前 promote）的草稿必然已落盘，re-promote 时 `fresh_write=False` → 传 `draft_sha256=None` → `store.promote` 不写 hash（`:509-528` None 语义=不动），用户照文案重跑 promote 后 hash 仍是 None，仍被同一分支拒绝——文案给出的补救无效。真正可行的两条路：`--force`，或先删草稿再 promote（fresh 写入才会记录基线）。建议把文案改成指向 `--force` / 删草稿重建。

### NIT-2 — fresh_write 的检查与 materialize 内的存在性检查之间存在 TOCTOU
`src/vibesop/cli/commands/skill_commands.py:1828-1829`

`fresh_write` 在 `materialize_candidate` 之前用 `exists()` 判定，而 `materialize_candidate` 内部才是权威的 no-overwrite（`skill_promote.py:1573-1577`）。若两进程并发 promote 同一 cluster，本进程可能把"对端刚写入的草稿字节"记为基线 hash。概率极低（同 cluster 并发），但仓库一贯的防御风格（双锁、flock）下，把"是否新鲜"判定并入 materialize 返回值会更稳。属加固建议，非缺陷。

### NIT-3 — 看板模块跨包导入私有符号
`src/vibesop/dashboard/_discoveries.py:51,82`

`_sanitize_body_text` 是 `skill_promote` 的私有函数（下划线前缀），被 dashboard 模块直接 import 使用。仓库有先例（CLI 的 `_redact_query` 同源构建，docstring 已注明），且属读路径非写入，仅轻微耦合；若再有第三处消费方，建议提为公开 helper。

### NIT-4 — `miss_share_by_layer` 统计口径正确但当前对真实数据恒为 "unknown 100%"
`src/vibesop/core/observability/skill_promote.py:1178-1205`

口径本身无误：与 `miss_pool_size` 用同一 `miss_spans` 池（`:958-960` 顺序赋值），`count/total` 且每个 span 恰好落一个桶，和恒为 1.0；`_miss_share_by_layer` 的 metadata 解析容错与 `is_route_miss_span` 一致（dict 或 JSON 字符串、坏 JSON 归 unknown）。但当前 route span 生产方（`agent_runtime` / `cli.main`）不写 `metadata.layer`，真实数据 100% 进 unknown——M4 的观测目标（上线前后各层 miss 份额对比、供 dismiss 熔断）在生产者补字段前实际不可用。docstring 已如实声明并 dogfood 验证，属诚实降级；放 residual risk 跟踪生产者侧补字段。

## Residual risks

1. **`--activate` 失败后行已 promoted**：`store.promote` 在守卫链之前执行，`--activate` 被拒（如未编辑）时候选已翻 promoted、草稿已落盘。语义上等于一次普通 promote（promote≠activate，草稿内也印了 "NOT yet registered"），但用户可能误以为"promoted=已激活"。可考虑在被拒分支补一句"候选已 promoted，但未注册"。
2. **非交互环境下的 `typer.confirm`**：全局激活的确认在无 TTY/EOF 时是 fail-closed（中止）而非放行，安全方向正确，但脚本化调用全局激活会被卡住/中止，未测该路径。
3. **`promote --activate` 恒走 LLM 自动配置**（`_auto_configure_skill_with_llm`，无 manual-config 选项）：行为与 `vibe skill add` 一致，失败有 fallback，但激活的耗时与交互取决于 LLM 环境。
4. **`miss_share_by_layer` 在生产者补 `layer` 前无观测价值**（见 NIT-4），需单独追踪生产方改动。
5. **双 scope 去重/信号并集与 CLI 的一致性靠两处独立实现**：`_discoveries.py` 的 `_load_scoped_candidates` 与 CLI `_gather_scoped_candidates` 逻辑逐行相同（含平局取 project 优先），但无共享单元；CLI 侧改动可能静默漂移看板。可用同一 helper 收敛。
