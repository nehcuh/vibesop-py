## 二、包末 6 个攻击点逐一回应

**1. OSA 转置偏差是否接受?是否引入新误匹配?**
偏差的动机成立:分母修复会把最典型转置 typo 清零,OSA 确实救回("reivew my code" 0.917)。实现本身正确(2 万对属性检查)。**但引入了一类可复现的新误匹配**:真实英语转置同形对在 0.7 阈值上通过——`form/from=0.75`、`trail/trial=0.8`、`angel/angle=0.8`、`dairy/diary=0.8`。端到端实测:单 token 查询 `"form"` 以 levenshtein@0.75 路由到 keyword 仅为 "from" 的技能;`"diary"`→"dairy"技能@0.8。CJK 侧:"配置门禁"↔"配置禁门" 0.75(typo,合理),"牛奶/奶牛""蜜蜂/蜂蜜" 0.5 被挡,风险低于拉丁侧。**裁决:接受偏差,但按 NIT 要求补一道防线**——给转置分支加 token 长度下限(≥6 可保留 reivew/review、configuartion/configuration,同时杀掉 form/from、trail/trial 等 4-5 字符对)。当前所有误匹配对被 should_enqueue 弱层规则送人审,爆炸半径受控,故不升级为 BLOCK。

**2. 两遍制副作用(优化上下文丢失/性能/线程安全)?**
- **优化上下文**:声明不实(见 A3)。第二遍 levenshtein 结果照常进 apply_optimizations(preference/instinct boost 仍可把它顶到 1.0),"不再进 apply_optimizations"是对代码的错误描述;实际改变的是"levenshtein 只在 calibrated 全 miss 后才运行"。
- **性能**:miss 路径 = 3 matcher 遍(第一遍 3 个 matcher + 第二遍 4 个 + `_finalize_no_match` transparent 回退扫描 `unified.py:931`/`result_mixin.py:284` 各 4 个)。命中路径反而更快(3 个 matcher)。"两倍"大致成立,miss 占比小,可接受。
- **线程安全与异常恢复**:异常恢复 ✅(`unified.py:770-772` finally 复原)。**但线程安全声明("concurrent routes can't observe the reduced list")是假的**——见下方附加问题 (a),BLOCK。

**3. no_match 不重复计 MissCounter 是否完备?**
完备性核对:no_match(含 FALLBACK_LLM sentinel,`has_match`=False)→ `_record_route_miss` 记一次,闸门跳过;low_confidence/user_correction → `_record_route_miss` 不触发,闸门记一次。无双计路径。漏计:非默认路径构造的 store,`_get_miss_counter` 返回 None → 只拦不记(已注释,可接受)。另发现 wrapped-junk 会漏进 miss counter(见附加 (c)),但那不是"双计"而是预存在的遥测卫生问题。

**4. token 判据本地复制漂移风险?**
现在实际是**三份**副本:KeywordMatcher(`strategies.py:140-145`)、LevenshteinMatcher(`:528-533`)、routing_pending(`:70-77`),tokenizer 共享。三者当前一致,但无任何漂移护栏(无共享 helper、无一致性测试)。NIT:建议抽公共函数或加一致性断言测试。

**5. 增量索引用私有方法的脆弱性?**
签名今日全兼容,降级路径全部不阻断(测试钉死)。脆弱点有二:(i) 私有方法无 API 契约,indexer 重构即静默破坏——注释已声明、建议收敛公开 API,合理;(ii) **global 分支是死路径**(见附加 (b)),比声明更弱。

**6. 拆 boost 后 decay 注释是否准确?**
准确。新注释正确描述了"仅 decay/负信号有真实外部来源/正信号只能来自显式确认",与代码逐条对应;僵尸注释(846-855)改写到位。

## 三、自行挖掘的包外问题

**(a) BLOCK — `_route_lock` 竞态可永久静默删除 levenshtein matcher。**
`unified.py:758` 在锁外读 `pipeline._matchers`,`:765-773` 锁内交换。交错:线程 A 换入 reduced 列表并运行第一遍;线程 B 在 A 的窗口内执行 `:758` 读到 **reduced 列表**并把它当作自己的 `full_matchers`;A 复原(4 项)释放锁;B 拿锁、换入自己的 calibrated(3 项)、finally 把 `pipeline._matchers` 复原为 **3 项**——levenshtein 被永久移除,直至进程重启。窗口会被 embedding encode(numpy/onnx,GIL 释放)自然放大。**压力测试 300/300 轮复现永久丢失**(第一遍人为 sleep 5ms 模拟慢 matcher)。修复两行:把 `:758` 的读取移进 `with self._route_lock` 内。且该函数是 `_route_lock` 唯一持有者,`unified.py:931`/`result_mixin.py:284` 的回退扫描均不带锁(影响小,但证伪了"concurrent routes can't observe the reduced list")。

**(b) NIT — 增量索引的 global 分支是死路径。**
`vibe skill add --global` 装到 `~/.vibe/.vibe/skills/<id>`(installer `project_path = Path.home()/".vibe"` + `_skills_dir`);而 `_index_newly_added_skill` 用 `SkillLoader(project_root=Path())`,`loader.py:78-92` 搜索路径只含 `<root>/skills`、`<root>/.vibe/skills`、`<root>/core/skills`、包内 builtins——**不含 `~/.vibe`**。[executed] 假 HOME 实测:global 技能 `get_skill` 返回 None → 恒走"not yet discoverable"降级。声明"合并进 project/global 层索引"对 global 不成立(项目层路径验证过可用)。降级文案诚实,无功能破损,但注释/声明应改为"增量索引仅对 project 安装生效"或接入正确搜索路径。

**(c) NIT — wrapped junk 仍漏进 miss counter。**
`<user_query><system-reminder>…</system-reminder></user_query>`:入口 junk 守卫(`unified.py:1010-1012`)在解包前看不到 wrapper → 解包后 `_single_skill_route` 守卫拒绝(匹配正确),但 `route()` 的遥测块(`:1023-1028`)仍对 junk 结果执行 `_record_route_miss`——破坏"junk 永不进 miss counter"的不变量(该不变量只对未包裹 junk 成立)。预存在(旧代码连拒绝都不做),但 M7 的解包让"内层 junk 被拒 + 仍被计数"这一半吊子状态浮现,建议解包后同步短路遥测。

**(d) NIT — dedup(hash-only)与 suppress((hash,skill))策略不一致。**
dismiss 只压制同 (hash,skill);同一垃圾 query 经不同 skill_id 重路由,次日可重新入队,绕过"垃圾 query 只占 1 槽"的 M7 本意。建议 suppress 同样改 hash-only。

**(e) NIT — dedup 按 hash 折叠会吞掉真实歧义信号。**
事故数据里 "review my code" 同时命中 kimi-gated-fix 与 fuck-my-shit-mountain 两行——这对人类审阅是"matcher 迷惑"的宝贵信号。闸门已按 token 过滤纯垃圾,hash 级折叠对"真实 query 命中 2 技能"也一视同仁砍掉第二行。建议:同一 hash 的后续项可折叠为同一条目的 alternatives 而非丢弃。

**(f) NIT — CJK 短确认语穿透闸门。**
"知道了"/"可以吗"实测**放行**(CJK 重叠 bigram 天然给 ≥2 个 meaningful token)。M7 dogfood 目标是消灭"确认类"噪讯,3+ 字中文确认语恰好躲过 token 规则。闸门偏保守属设计选择,但按声明目标("7/7 项都是低信息垃圾")建议补常用中文确认语 stopword 或接受此漏洞并注释。

**(g) NIT — 闸门在 store 层而非 router 层,语义双轨。**
`should_enqueue_from_route` 的 docstring 已注明分工;但闸门只挡 `try_enqueue`,绕过 store 直接写 pending 的未来路径(或 `user_correction` 直写)不受保护。今日无此路径,属设计残留。

## 四、结论

**BLOCK** —— 唯一阻断项:**(a) `_route_lock` 竞态导致 levenshtein matcher 被永久静默移除**(`unified.py:758` 锁外读取 + `:772` 用陈旧引用复原),300/300 复现,修复 2 行(把读取移进锁内)。该缺陷恰好落在指令要求重点审查的轴线上,且与代码自身注释宣称的线程安全保证直接矛盾。

三处主动声明裁决:
- **OSA 转置:接受**,但引入新误匹配类(form/from 等 0.75-0.8 端到端可路由),按 NIT 建议加长度下限;
- **两遍制副作用:接受设计、驳回依据**——"levenshtein 不进 apply_optimizations"与代码/插桩不符,且线程安全声明不成立(即 BLOCK 项);
- **no_match 不双计:接受**,核对完备,无双计/漏计路径。

其余全部 NIT(global 索引死路径、wrapped-junk 遥测、dedup/suppress 不一致、歧义信号折叠、CJK 确认语穿透、判据三副本漂移、miss 路径三遍性能)。修复 (a) 后即 PASS_WITH_NITS。
