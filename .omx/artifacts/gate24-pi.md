## Verification performed

## Verdict: PASS_WITH_NITS

The gate itself is correct, honest, and well-tested; the divergent deviation is justified and consistently applied; the join is sound on real data. One MAJOR finding is on the **calibration tooling's future recheck path** (latent today, data-confirmed vector), plus nits.

## Findings

**1. MAJOR — Calibration labeling leaks same-trace pairs across candidate clusters (latent today, data-confirmed).**
`scripts/calibrate_behavior_threshold.py:57-75` (`collect_cluster_sequences`) attributes each trace to **every** candidate whose `task_ids` contains its task_id; `score_pairs` (:79-102) then pairs across clusters with no dedup by trace identity. In the current cmspark pool **254 task_ids span ≥2 candidates** (68 gold+miss overlaps, 161 gold+gold across scan windows — verified). When the documented recheck trigger fires (any cluster ≥2 sequences), a tool-bearing task_id in two candidates yields a **same-trace pair labeled negative at Jaccard 1.0**, corrupting pair counts and the decision band (high-Jaccard "negatives" also inflate false-consistent error at high t, biasing the band downward). Duplicate-cluster_id rows would additionally create positive self-pairs. Today it's harmless (the 2 tool-bearing task_ids are disjoint; the 0.300 pair is genuine — verified distinct traces), so the gate is unaffected. **Fix before recheck: dedup entries by trace identity (route span id / trace_id), or restrict to one scan's clusters.** Residual risk: if unfixed, the next calibration can emit a confidently-wrong decision band — the exact failure this discipline was built to avoid.

**2. NIT — Divergent: justified and consistent, but the design doc itself wasn't updated.**
`.omx/artifacts/m12-product-design.md:66` still documents two states (`consistent / unavailable`). The deviation is well-reasoned ("有数据且低于阈值" cannot honestly be "unavailable"; the design's own 诚实标注 principle demands the third state) and documented in the calibration record + `behavior_consistency.py` module docstring + `discovery.behavior_evidence_label` docstring. Applied consistently everywhere: state machine (`behavior_consistency.py:141-166`), validation set (`skill_promote.py:94`), label fn (`discovery.py:140`), CLI render (`skill_commands.py:2363-2366`), dashboard passthrough, and tests (unit, scan-rescan, 4-state CLI render all pass). Update the design doc line for contract traceability.

**3. NIT — `behavior_spans` pre-age-out capture is scoped to behavior only, but the comment overstates the scoping.**
`skill_promote.py:1180` claims legacy tool spans' "PARENT route span already passed the filter". The join matches by bare `task_id` against **all** pre-filter route spans, so tool spans under **legacy routes** (`project_id=="default"`, age-out-excluded from clustering) also contribute when their task_id matches a candidate — the parent did *not* pass the filter. Verified `behavior_spans` is consumed only by `assess_behavior_consistency` (:1314, :1367) — no leak into clustering/miss/spans consumers. Legacy recurrences can flip verdicts in both directions (raise n toward consistent, or lower mean toward divergent). Defensible (older recurrences are still recurrences of the pattern), but correct the comment.

**4. NIT — Join docstring says "parent primary / trace fallback", code is an OR-union.**
`behavior_consistency.py:76-82` vs `:113-115`. The union is actually the safer direction (keeps tool spans whose parent is a nested non-route subtask within a candidate trace — strict parent-priority would drop them), and on real data both keys agree 159/159. One contrived residual: `key` (:118-120) prefers `trace_id` even when attribution came via parent — a wrong-but-present trace_id with a candidate parent would group spans under the wrong trace key. No current-data impact; align docstring with code.

**5. NIT — Single-tool-trace exclusion creates a tool-set blind spot.**
`behavior_consistency.py:158-166`: single-tool traces are dropped from both `n` and the score, so tool-**set** divergence is invisible — `[Read,Grep]×2 + [Read]×1` → `n=2`, score `1.0` → `consistent`, while a third of recurrences used a disjoint tool set. The fold compounds this (a 50×Read trace collapses to single-tool → excluded entirely). The exclusion is the most honest of the three options (empty-bigram Jaccard=0 → "divergent" would mislabel two identical single-tool traces; counting them as trivially consistent over-claims), and it protects against legacy single-tool noise (7/10 cmspark traces are single-tool). Acceptable, but note the residual: `consistent` can over-claim on clusters with single-tool outliers.

**6. NIT — No in-module validation of threshold/score.**
`assess_behavior_consistency` accepts any `threshold` (only the CLI validates `[0,1]` at `skill_commands.py:1411-1415`); a programmatic caller passing `1.5` silently flips all verdicts to divergent. `behavior_score` from_dict accepts non-float (hand-edited `"0.9"` string passes; inert since `evidence_score` doesn't consume it — verified `discovery.py:146-160`), asymmetric with the strict `behavior_evidence` validation.

**7. NIT — Constant duplication + stale comment.**
`_VALID_BEHAVIOR_STATES` is defined twice (`behavior_consistency.py:42`, `skill_promote.py:94`) — drift risk if a 4th state is added to one file only. `discovery.py:465` `DiscoveryRow.behavior` comment still reads `# consistent / unavailable / not_collected` (missing divergent).

**8. NIT — Calibration tooling hygiene.**
(a) `report()` returns exit code 0 on `SAMPLE TOO THIN` — fine as a doc artifact, but cannot fail closed if ever gated. (b) Artifact drift: `m3-behavior-calibration.md` says "25 rows / 152/159 parent hits"; current pool is 28 rows / 159/159 — the record predates later scans; the recheck trigger must re-run the script, not trust the stale counts.

**9. NIT — Test gaps (11 unit + 3 scan + CLI + serialization tests otherwise lock the three states, join rules, and the pre-age-out capture well — `TestBehaviorEvidence` tool spans deliberately omit `project_id` and still count, which pins finding 3's scope).**
