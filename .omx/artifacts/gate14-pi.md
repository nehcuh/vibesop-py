## Blocking issue

**BLOCK-1 — `ANCHOR_STOPWORDS` is incomplete, and its omission lets the exact failure class the milestone claims to kill through the anchor gate.** (`src/vibesop/core/matching/idf.py:43-75`)

The list's stated rationale (idf.py:27-31, config `keyword_anchor_idf_min`): function words are *rare* in a skill-catalog corpus (high IDF) yet semantically empty, so they must be excluded from anchor eligibility. But the list contains only 33 words and omits most of the function words that are in fact rare in this corpus. On the real 239-candidate pool, these have `w ≥ 0.78` (the anchor bar) and are **not** in the list: `get` 0.830, `make` 0.830, `can` 0.786, `but` 1.0, `they` 0.786, `will` 1.0, `was` 0.893, `which` 0.893, `why` 0.830, `who` 1.0, `there`/`here` 1.0, `should`/`would`/`could`/`may`/`might`/`must` 0.83-1.0, `after` 0.893, `between`/`while` 0.830, `because`/`during`/`again`/`too`/`same`/`some`/`most` 1.0. Notably, the canonical tokenizer's own `DEFAULT_STOP_WORDS` contains `from/use/can/get/make/go` — none of which made it into `ANCHOR_STOPWORDS`.

**Demonstrated mis-fire on the real code + real pool** (default config): query `get this working on the new branch before the deadline` scores **0.332** against `mattpocock/grill-me` — above the default 0.3 matcher floor, above the 0.25 cap. The TFIDF gate shares the same gap (same `find_anchors`; `_has_anchor` returns True for the same query).

**Why this blocks**: the milestone's documented guarantee (config `keyword_anchor_cap`, CHANGELOG, docs) is that anchorless/function-word matches "abstain even on installations whose `routing.min_confidence` preference has not been raised to 0.6". The demonstrated query's *only* anchor is the function word `get`; on a default-config installation the matcher pipeline accepts grill-me at 0.332. The eval sets don't contain this case (hence no regression), but it is exactly the out-of-set structural risk focus #2 asks about. It does **not** reach the production 0.6 floor, so current installs are unaffected — but the safety property the milestone is built on is leaky.

**Minimal fix**: complete the frozenset (a superset of `DEFAULT_STOP_WORDS` plus the standard function-word set suffices) and add a unit test pinning that a function word (e.g. `get`, `make`, `because`) present in a candidate's *description* never anchors.

VERDICT: BLOCK

Blocking: incomplete `ANCHOR_STOPWORDS` (`src/vibesop/core/matching/idf.py:43-75`) — common function words rare in the skill corpus (`get` 0.830, `make` 0.830, `can` 0.786, `because`/`will`/`who`/`there`/`should`/`would`/`could`/`most`/`same`/`some`/`such` 1.0, etc.) are eligible anchors; demonstrated on the real pool that "get this working on the new branch before the deadline" scores 0.332 > 0.3 default floor against `mattpocock/grill-me` via a description-only `get` anchor, violating the documented "anchorless/function-word matches abstain below the matcher floor" guarantee.
