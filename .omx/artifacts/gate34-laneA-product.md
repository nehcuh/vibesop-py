# Gate34 Lane A 评审报告：D1–D4 产品/用户价值视角

评审人立场：独立产品判断，不迎合既有排序。所有判断已对照代码核实（`src/vibesop/core/observability/skill_promote.py`、`clustering.py`、`gold_detection.py`、`dashboard/_discoveries.py`、`scripts/replay_routing_baseline.py`、`src/vibesop/cli/commands/skill_commands.py`）。

## 一、逐向评估

### D2 子代理轨迹去重 —— 用户价值最高，成本最低

- **解决什么痛点**：用户第一吐槽"发现队列一半是垃圾回声"。这不是感受问题，是实测数据：cmspark miss 池约 64% 是子代理 prompt 回声/机器包装（gate32 A1 注释，`skill_promote.py:341-349`）。队列里每一张垃圾卡片都在消耗用户的审查注意力——而人审是这个系统的定价闸门，闸门被垃圾淹没，整个闭环的实际吞吐量就减半。
- **用户能看见什么**：`vibe skill discover` 和看板 Discoveries 页里垃圾卡片消失；scan summary 里多一行"已过滤 N 条机器形状 query"（这个数字本身就是价值信号，让用户信任过滤在干活）。
- **不做的代价**：D1 的 verifier 指标会被污染——对着一半是回声的 cluster 算"捕获率"，数字没有意义。**D2 是 D1 的前置条件，不是并列项**。
- **负面风险**：`_is_agent_prompt_shape`（`skill_promote.py:366`）里 `_AGENT_PROMPT_MAX_LEN = 150`——真实用户指令超过 150 字符会被误过滤。该谓词当前只用于草稿 trigger 预填（误杀代价=人工手写 trigger），挪到 intake 后误杀代价升级为**真实需求永远进不了候选池**。必须加护栏：被过滤的 query 不删除，只标记不入聚类，并保留可审计的过滤样本日志。
- **结论**：现有资产复用度最高（谓词已存在且有测试），改动面小（intake 一处 + cluster 内折叠 + gold rate 口径），直接命中用户最大痛点。**应排第一。**

### D1 Promote verifier —— 对症但治标，且 FAIL 呈现方式决定成败

- **解决什么痛点**：用户第二吐槽"promote 出来的技能是空壳"。但要分清两层：(a) 草稿内容本身空洞（draft 生成质量），(b) 激活后稀释路由（行为后果）。D1 只检测 (b)，不解决 (a)。现有 M5 编辑护栏（`draft_sha256`，`skill_commands.py:2032`）已经挡了"未编辑就激活"，但挡不住"编辑了但内容仍然稀烂"。
- **用户能看见什么**：promote 后一行影子回放结论："该技能能接住本簇 12/15 条 query，会抢走现存命中 0 条 → verify: PASS"。这是把"凭感觉 promote"变成"看数据 promote"，是闭环里目前唯一缺失的反馈环节。
- **不做的代价**：每个空壳技能激活后都在侵蚀路由质量，而用户要等下次 miss 才发现——信任是单向流失的。
- **负面风险（重点）**：误报 FAIL 比没有 verifier 更糟——用户按流程走完 promote，被一个他无法解释的 FAIL 拦住，挫败感直接打到"这系统是不是在刁难我"。三条硬性缓解：
  1. verify 结果默认是**建议性徽章**（PASS/WARN/FAIL + 理由），不是硬阻断；硬阻断仅限 `--activate` 路径且 FAIL 必须附可操作的失败明细（哪几条 query 没接住、各自最近邻是谁）。
  2. FAIL 判定阈值必须先拿真实数据标定一轮（直接复用 `replay_routing_baseline.py` 的 shadow/hijack 机制，这脚本已经能算 hijack risk），不能拍脑袋定 0.6。
  3. 看板上 FAIL 卡片必须能展开看证据，不允许只有一个红标。
- **额外产品建议**：把"草稿内容质量"纳入同阶段——verifier 之外，draft 预填时用 `core_steps`（已有 step 频率标注）生成骨架而不是空模板。用户要的是"promote 出来就是能用的技能"，检测空壳只是兜底。
- **结论**：真实价值、资产可复用，但工程量和标定依赖都比 D2 重，且指标质量依赖 D2 先清池。**排第二，紧随 D2。**

### D3 分源阈值 —— 对用户不可见，且现在没有数据支撑

- **解决什么痛点**：间接的——更准的入池门让队列更干净。但用户看不到、也不需要看到"miss 源的阈值是 0.63 而 gold 源是 0.58"。
- **现实约束**：依赖 M3 阈值复检数据，而该数据"等候选簇攒数据"——即依赖项本身在挂着。在数据到位前做 D3 是把拍脑袋阈值换成另一个拍脑袋阈值。
- **负面风险**：分源阈值引入新的不可解释性——用户会发现两个看起来差不多的候选一个进池一个没进，没有解释层就是"系统行为飘忽"。
- **结论**：**降为数据成熟后的调参任务，不单独立项**。D2 落地后候选源分布会变（回声被清掉，miss_recurrence 占比上升），届时用真实分布一次性标定即可。它不是产品方向，是 D2 的后续校准动作。

### D4 不可变路由记录 —— 纯基础设施，当前无人受益

- **解决什么痛点**：没有用户痛点。hash chain 服务的是"回放/标定结论可审计"——但目前的回放和标定是单人 dogfood 场景，作者即审计者，链完整性保护的是"防止自己骗自己"，收益接近于零。
- **不做的代价**：几乎没有。若未来要把标定结论对外发布（开源社区、多用户信任），再补不迟。
- **负面风险**：span 写路径是所有平台的公共热路径，改动格式要回归 6041 个测试基线 + 多平台适配，成本真实、收益虚拟。span_writer.py 目前无任何 hash 链痕迹（已 grep 确认），是从零建设。
- **结论**：**明确推迟**。除非出现"标定结论需要第三方采信"的具体场景，否则不进入路线。

## 二、列表外更值得做的方向

### N1（新增，最高性价比）：队列与看板的可解释性修复

用户第三吐槽"表格列含义看不懂"。这是**纯文案/展示层问题，成本以小时计，收益立即可见**。具体：
- CLI 表格列头改自解释命名（如 `gold_rate` → `成功率`），`vibe skill discover --help` 加一段三行的字段词汇表。
- 看板卡片加 tooltip/展开说明（`_discoveries.py` 的卡片字段已有 `source`、`cooling` 等概念，对外无定义）。
- 每张卡片加一行"为什么它在这里"（入池原因：成功率≥60% / miss 跨 2 天复现 3 次），数据都在 `ClusterCandidate` 里，只差渲染。

产品视角下这条比 D3、D4 都值钱：用户看不懂列 → 无法做 promote/dismiss 判断 → 人审闸门失灵 → 闭环空转。它和 D2 是同一件事的两面：D2 让队列内容可信，N1 让队列可读。

### N2（新增，中期）：路由命中解释

"这条 query 为什么路由到这个技能"目前用户无从得知。D1 的 verifier 顺手就能产出这个（回放时记录最近邻）。不做成独立功能，作为 D1 交付物的副产品暴露 `--explain` 即可，零额外架构成本。

## 三、独立排序与实施路线

我的排序：**N1 ≈ D2（并行）→ D1 → D3（并入 D1 标定）→ D4（推迟）**。与初步排序 D1→D2→D3→D4 不同，理由：

1. **D2 先于 D1**：D1 的两个核心指标（捕获率/误劫持率）对着含 64% 回声的 cluster 算出来是不可采信的数字；清池先行是数据卫生，不是偏好。且 D2 成本远低于 D1，先交付先见效。
2. **N1 提到最前**：成本最低、直接命中用户第三条吐槽、无风险，且让后续 D1 的 verify 徽章有地方放。
3. **D3 降级为校准动作**：依赖数据未到位，单独立项是空转。
4. **D4 推迟**：无人受益的基础设施，当前阶段是负 ROI。

### 阶段划分

**阶段 1（1–2 天）：可读性 + 清池**
- 交付物：N1 全套（列头重命名、help 词汇表、看板 tooltip、"为什么在这里"行）；D2 intake 过滤（复用 `_is_agent_prompt_shape`）+ cluster 内 Jaccard>0.8 近重复折叠 + gold rate 按去重后口径 + scan summary 的"已过滤 N 条"计数与样本日志。
- 用户可见变化：队列里回声卡片消失；每列含义一看就懂。

**阶段 2（3–5 天）：promote verifier**
- 交付物：D1 影子回放（复用 `replay_routing_baseline.py` 的 shadow/hijack 机制，封装为 `promote` 流程内一步）；verify 结果以建议性徽章进 CLI 输出和看板卡片；FAIL 必附明细；草稿骨架用 `core_steps` 预填；附带 `--explain`（N2 副产品）。
- 用户可见变化：promote 后立刻看到"能接住 X/Y 条，会抢 0 条 → PASS"；激活前不再开盲盒。

**阶段 3（数据到位后，不排期）：分源阈值标定**
- 触发条件：D2 落地后候选池攒够 ≥30 个不同源的 promote 结果（含成败标签）。

**阶段 4（推迟）：D4 不可变记录**
- 仅在出现"标定结论需第三方采信"场景时立项。当前不做。

## 四、验收标准的"用户可感知"定义

**N1 可解释性**：没读过代码的用户看 `vibe skill discover` 输出，能在不看文档的情况下说清每列含义。操作化：列头全部自解释中文；`--help` 含 ≤5 行词汇表；随机抽 5 张卡片，"为什么在这里"行与 `ClusterCandidate` 实际入池字段一致（防文案说谎）。

**D2 去重**：打开发现队列翻 20 张卡片，机器回声 ≤1 张（从 ~50% 降到 ≤5%）。操作化：(a) 存量池回放回声形状卡片清除率 ≥90%；(b) 误杀率用 must-NOT-catch 反例测试守住；(c) scan summary 打印过滤计数；(d) 被过滤 query 留审计日志，误杀可翻案。

**D1 verifier**：promote 任意候选，30 秒内看到一行结论并能回答"这个技能接得住它该接的 query 吗？会伤到现有路由吗？"。操作化：(a) 已知良好历史 cluster promote → PASS；(b) 回声 cluster promote → WARN/FAIL 且明细列出未捕获 query 及最近邻；(c) FAIL 误报率用真实标定守住（人工复核 FAIL 案例，真实坏技能占比 ≥80%）；(d) verify 永不静默阻断——用户始终能 `--force`，但 force 被记录。

**D3 分源阈值**：用户什么都不用配，队列垃圾率在下一次扫描后进一步下降。操作化：上线前后各跑一次全量 scan，人工抽检 precision 提升且无一源召回归零。

**D4（若启动）**：唯一可见面是 replay 输出末尾一行"链校验：通过 / 断于第 N 行"。操作化：篡改测试（改历史行 → 校验必报断裂位置）。

## 五、一句话总结

先治用户体验（N1 可读性 + D2 清池，便宜且直击前两条吐槽），再补决策反馈（D1 verifier，但 FAIL 必须是可解释的建议而非黑盒阻断）；D3 是数据成熟后的调参、D4 是当前无人买单的基建，两者都不配占用现在的排期。
