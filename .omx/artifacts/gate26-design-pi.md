### 1. BLOCK — `os.chdir(exec_root)` around `handle_query` does not re-point AgentRuntime's project_root

`tick` constructs `AgentRuntime()` **once**, before the per-spec loop (`loop_cmd.py`). `AgentRuntime.__init__` freezes `self.project_root = Path(project_root).resolve()` with default `"."` — i.e. resolved against the tick's ambient cwd at construction time (`agent_runtime.py:277-278`). Every downstream component (`AgentRouter`, `SkillInjector`, `LightweightRouter`, `SlashCommandExecutor`, `PlanExecutor`, `StepContextInjector`, and the hint-path `user_root = self.project_root or Path.cwd()` at line 193, which is dead because `project_root` is always truthy) reads the **frozen** `self.project_root`. A grep confirms exactly one `Path.cwd()` reference in the entire runtime/router/injector tree, and it's unreachable.

So chdir-in-executor changes the process cwd but not the frozen `Path` — **project A's loop ticked from project B still routes against B's root**, which is precisely the cross-project bug the design exists to fix. Chdir would only affect subprocesses that inherit cwd during routing, and the command path already fixes itself explicitly via `subprocess.run(cwd=...)`.

The executor also *can't* fix this itself — the whole point of the runtime injection was to keep `core/loop` from importing the agent layer.

**Required fix:** per-loop runtime construction in the CLI (which is allowed to import agent):
```python
for spec in triggered:
    exec_root = Path(spec.project_root).resolve() if spec.project_root else None
    if exec_root:
        prev = Path.cwd(); os.chdir(exec_root)
        try:
            runtime = AgentRuntime()   # resolves "." against exec_root
            record = execute_loop_tick(spec, runtime=runtime, store=store)
        finally:
            os.chdir(prev)
    else:
        record = execute_loop_tick(spec, runtime=runtime, store=store)
```
chdir **before** construction, not around `handle_query`. AgentRuntime is lazily component-initialized, so per-tick construction is cheap next to the LLM call. Alternative: a `project_root` re-point method on AgentRuntime; or subprocess-per-tick isolation (heavier, unnecessary). The serial-tick precondition is enforceable (CLI loop is serial, launchd is one process per plist, the fcntl tick lock already serializes same-loop ticks) — but note chdir makes *cwd correctness* dependent on it too, which is a second reason to avoid chdir as the fix.

### 2. HIGH — The downgrade isn't "refuse", it's "quarantine" — warning must be precise

`store.py:_load_model` renames any file that fails `ValidationError` to `spec.json.corrupt` (forensics backup). An old build reading a new spec.json with `project_root` won't just refuse — it **renames the user's spec to `.corrupt`**, the loop vanishes from `list_specs`, and a subsequent old-build `create <same-name>` (collision check sees `None`) silently shadows it; `delete` would `rmtree` the backup. The CHANGELOG warning must say: *"older builds rename your spec.json to spec.json.corrupt and the loop appears deleted — do not run them against a v1.1 store; back up `~/.vibe/loops/` before downgrading."* (Design intent is right; the teeth are missing.)

### 3. MEDIUM — The None double-meaning leaks into backfill, not execution

For *execution* the None double-meaning is fine (legacy and deliberate-global behave identically: run from any cwd). But it leaks into **`install-launchd` backfills if None** and **`migrate-ownership`**: a user who explicitly does `create --global`, then runs `install-launchd` (which always writes `WorkingDirectory`), gets their deliberate-global loop silently re-pinned by the backfill — before migrate-ownership even runs. Dry-run-first + enumerated pin changes mitigate, but the honest fix is one line of doc on `create --global`: *"install-launchd / migrate-ownership will pin this loop; recreate with --global to unpin"* — plus confirm-by-default on migrate-ownership. Acceptable with that documentation.

### 4. MEDIUM — `create` pins raw cwd with no project-root validation

`install-launchd` gates on `_is_project_root_trusted` (`.git/` or `pyproject.toml`), but `create` pins whatever cwd is. Two failure modes: `create` in `$HOME` pins `$HOME`, and since `_owns` is "cwd-is-within-project_root", a `$HOME`-pinned loop is "owned" from almost everywhere — the filter silently degrades to status quo. Conversely `create` from a deep subdir pins the subdir, so bare `tick` from the project root *skips* it (surprising). Recommend: reuse `_is_project_root_trusted` at create (warn, `--global` escapes), or walk up **once at create time** to the nearest project root — that's a bounded create-time walk, not the tick-time walk-up infra the design correctly rejected. At minimum, document that create pins the literal cwd.

### 5. MEDIUM — Missing-exec_root → PERMANENT is right, but unspecified where it happens

Category choice is correct: TRANSIENT would retry into DEAD anyway while spinning, and skip-with-warning recreates the silent mis-attribution. But the design doesn't specify the mechanism: the executor has no pre-flight failure path today. The routing path needs an explicit `exec_root.is_dir()` check before `handle_query` fabricating a PERMANENT `FailureInfo` with a correct suggestion ("project root missing — re-run `vibe loop adopt`"). And the command path's `subprocess.run(cwd=missing)` currently lands in the `except OSError` branch with a **misleading** suggestion ("Check VIBESOP_RUN_PREFIX / uv installation") — that branch needs to distinguish missing-cwd from missing-uv. Also note "loud" is bounded: once DEAD, `_SKIP_STATUSES` silences the loop entirely — consistent with existing semantics, but worth stating.

### 6. LOW-MEDIUM — state.json embedded-spec staleness

`load_state` returns the `LoopState` whose embedded spec is whatever the last `save_state` captured. After adopt/migrate rewrites spec.json, state.json still embeds `project_root=None` until the next successful tick. Harmless for execution (executor uses the caller's fresh spec; only `record_run` reads `state.spec.max_failures` — a pre-existing staleness), so "stale copies harmless" is ~true. Recommend adopt/migrate also `save_state` (or document state.spec as always-stale-by-design). Also: the no-downgrade quarantine applies to state.json too (old build fails `LoopState` validation) — moot because `load_state` short-circuits on spec.json failing first, but the finding-2 warning should cover both files.

### 7. LOW — migrate-ownership platform/edge details

No `LaunchAgents/` on non-macOS (no-op vs error unspecified); plists whose spec was deleted (skip+warn); duplicate plists; hand-edited relative `project_root` (recommend `resolve()` in the executor at load). All minor.
