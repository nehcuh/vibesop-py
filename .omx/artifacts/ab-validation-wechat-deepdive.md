# 我们做了 6 轮 A/B 实验，试图证明"给 AI 装技能"有用——结果四次打平

> 一个 AI 技能路由系统的诚实验证笔记
> VibeSOP 效果验证全记录（2026-08-28 ~ 08-30）

## 引子：先说结论，再说为什么这个"失败"有价值

我们在做 VibeSOP——一套给 AI 编码代理（Claude Code、Grok Build 这类工具）做技能路由和编排的系统。核心信仰很朴素：**给 AI 一个技能库，在合适的时机注入合适的技能，AI 会干得更好。**

这个信仰几乎是中国式 AI 创业的主流叙事。但它经不起一个最基础的问题：**你怎么证明技能真的有用？**

于是我们决定用最笨的办法回答：双容器 A/B 对照实验，一个装 VibeSOP，一个裸奔，同样的任务、同样的种子、同样的参数，跑了六轮。

结果是：

- **四轮产物完全平手**（同样是 12/12 验收通过、同样的技术选型、同样的评分 23.5 vs 23.5）；
- 成本（耗时）指标方向乱跳，被迫撤回结论；
- 一轮换弱模型后出现了巨大的完成度差距——但深挖机制后发现，**赢的那一侧根本没用上任何技能内容**；
- 顺带揪出了自家路由层的真实 bug（7 个不该注入的查询 5 个被误注入）。

这篇文章完整复盘：设计目的、实验方法、踩过的坑、以及我们目前敢下和不敢下的结论。所有实验记录、预注册文档都在开源仓库里，欢迎复核。

## 一、设计目的：我们要回答什么问题

总问题拆成三个可检验的子问题：

1. **产物层**：有技能的 AI 写出来的东西，质量是否更高？
2. **过程层**：技能是否改变了 AI 的做事方式（哪怕产物相同）？
3. **成本层**：技能带来的增益，相对它消耗的时间/token 是否划算？

有一个隐含前提必须先成立：**路由层自身要干净**——该注入时注入，不该注入时不添乱。这个前提后来被证明是最先崩的，也是最有价值的发现。

### 为什么大多数团队不做这个验证

因为 A/B 一个"提示词层产品"极难：模型有随机性、任务有难度分布、评分有主观性。做一次不够，做多次贵。更容易的路径是挑一个好的 demo 场景发视频。

我们选择做，是因为一个更冷的事实：**如果技能的价值只能在精心挑选的 demo 里显形，那它就不是产品价值，是剪辑价值。**

## 二、设计方法：把"公平"做成 checklist

### 2.1 单变量对照

每轮实验只有两个容器，同一镜像（`vibesop-ab:base`，固定 Node/uv/rust/grok 版本）：

- **treatment**：装 VibeSOP（技能宇宙 + 路由 hook + 协议规则）
- **control**：裸环境

其余一切对齐：同一份任务书、同一个随机种子、同样的 CLI 参数（禁子代理、禁联网、同样的最大轮数）。任务书和三方库种子的 SHA256 逐字校验，防止"题目不一样"的质疑。

### 2.2 预注册制：防止事后诸葛

从第 5 轮开始引入**预注册**——在按下运行键之前，把三样东西写死：

1. **预测**：明确写"T 组得分高于 C 组 ≥3 分"这样的可证伪预测，连反向假设（技能注入是净伤害）也一并写上；
2. **评分表**：5 个维度 × 5 分的 rubric，每个维度的判分标准逐字固定；
3. **判读规则**：实验跑完后允许做什么判断、什么情况判无效重跑，全部提前锁定。

这一步的价值在后面会反复显现：当你盯着"平手"结果试图找话说的时候，预注册文档会拦住你。

### 2.3 有效性三验：确认"处理"真的发生了

A/B 最阴的坑是**处理组没吃到处理**。每轮结束我们验证三件事：

- 路由 hook 确实在运行时段触发过（看 span 日志）；
- 处理组的对话里真的出现了技能消费（读技能文档、调用路由 CLI 的记录）；
- 路由用的模型与设计一致（看延迟特征和日志里的模型名）。

第三条在弱模型轮抓到一个静默失败——后面细说。

### 2.4 双向隐藏测试

调试任务（第 3 轮）用了"植入 bug 的代码库"：种子代码里埋了 4 个真实 bug，隐藏验收测试只在我们手里，跑完即删。两组都看不见测试，防止"面向测试编码"。

## 三、六轮实验全景

| 轮 | 任务 | 方法升级 | 结果 |
|---|---|---|---|
| R1 | 简单 todo CLI | 双容器 + 隐藏验收 | **平手**（12/12 等价） |
| R2 | 同 R1 | 技能宇宙×3（预装三个技能包） | **平手**（12/12 等价） |
| R3 | 调试任务（4 个植入 bug） | 双向隐藏测试 + 过程层对比 | **产物平手**；过程有差异（见 §5.1） |
| R4 | —（方法论评审） | 外部模型五路独立对抗仲裁 | 否决了有偏的原方案 |
| R5 | 喷气发动机 3D 教学网页 | 预注册制 + 双轮人评 | **平手**（23.5 / 23.5） |
| R6 | 同 R5，换 27B 弱模型 | 路由 LLM 同步换弱模型 | **完成度差距极大，但机制意外** |

R5 的任务是我们特意选的"技能应该占优"的场景：规格留白、需要教学法设计、需要物理建模。强模型两组都交出了 10 文件级别的完整应用，5 维评分一毫不含糊地打平。

R6 换成 27B 本地弱模型后（编码模型和路由模型同时换，保证公平），结果出现了戏剧性分化——这是全文最重要的部分，放在 §5.3。

## 四、中间遇到的问题与解法（工程实录）

这部分是给真正想复现类似实验的同学的。问题按四类。

### 4.1 基建类

| 问题 | 解法 |
|---|---|
| 容器里 CLI 鉴权 15 小时过期 | 一次性 token，实验前重发 |
| headless 模式卡在权限确认 | 必须开 `--always-approve` |
| 解包产物 uid 错乱 / git 拒读 | tar 时归一 uid + `safe.directory` |
| 上一轮残留的元数据文件让监控误判"已完成" | 每轮跑前清空 `/tmp` 状态文件，监控改看进程数 + 会话事件 |

教训：**实验基建的"陈旧状态"比 bug 更危险**——它不报错，只让你的观测悄悄说谎。

### 4.2 弱模型特有（R6 三连击）

这是本次最有含金量的坑：

1. **token 截断被当错误**。弱模型推理链长，超过单次输出上限时，推理服务器把"截断"当作错误上报，整个运行直接终止（rc=1，零产物）。解法：把上限从 8192 提到 32768，双臂同步改。
2. **思考循环**。弱模型会在单轮里无限思考——我们观测到一次 45 分钟、11006 个思考事件、**零工具调用**的运行，直到撞上限死亡。解法：runner 加 `--reasoning-effort low --no-plan`（双臂同步），小任务验证思考事件从 11006 降到 15。
3. **路由模型静默丢失**。处理组的路由 LLM 配置了弱模型，但框架的工厂函数没有透传模型名，静默回退到一个硬编码默认名——而这个模型在服务器上不存在，路由调用 52ms 内 404，系统无声降级到无 LLM 模式。**表面一切正常，公平性已被破坏。** 解法：环境变量显式指定，并用 span 日志验证路由真的打到了弱模型（延迟 18 秒、日志带模型名）。

第 3 条是"有效性三验"存在的全部意义：没有它，我们会拿着一个"路由用了强模型"的假实验写结论。

4. **超长上下文中止**。处理组跑了 5.5 小时、累计输入 810 万 token 后，推理服务器内存守卫在预填充阶段中止了请求。裁定：所有交付文件在中止前已写完，故障只吞掉了收尾说明——按预注册规则记录在案、不判无效。

### 4.3 方法论类

- **墙钟时间不可作判据**：四轮耗时比 1.8× → 交叉 → 1.9× → 0.82×（反向），任何方向都能被噪声支持。正式撤回早先"技能有可见时间成本"的说法。
- **一次实验推翻一次设计**：原计划的 Web 基准测试方案被外部模型五路对抗评审 5/5 否决（工具变量不可控），改用容器内任务书方案。
- **评审要多元化**：我们的流程逐渐固定为"设计评审走双外部模型 + 交叉"，两路视角互补——一个抓数据/结构层，一个抓产品/认知层。多处单路漏掉的 must-fix 被另一路抓到。

### 4.4 顺带发现的 CI 时序坑

验证期间一次纯文档提交让 CI 连续两轮变红。排查发现是一个并行度测试的时序断言（8×50ms 并行应 <250ms）被变慢的 runner 击穿（实测 0.31s）。修复不是简单把线挪到 0.32，而是**把人工延迟加倍到 120ms**——让"并行通过线"和"串行基线（960ms）失败线"两侧都有厚裕度。只挪线的话，下次 runner 再漂移还会 flake。

### 4.5 路由精度审计：A/B 之外的真 bug

A/B 的前提是路由干净。我们拿 7 个"不该注入技能"的日常查询（聊天、评审、翻译）实测：**5 个被误注入**，且置信度恒定显示 82%——非结构化回复被硬编码成了固定置信度。根因四个（提示词没有 no-match 出口/置信度硬编码/缓存污染/信封未解包），六次提交全修：

- 修复后同 7 探针 **0/7 误报**，正例 3/3 保持命中；
- 建了 22 负 + 8 正的 held-out 资产常态化回归这道门；
- 修复本身又过了一轮五路对抗复审。

讽刺的注脚：写这篇文章的当天，我们自己的路由层又把"写一篇公众号总结"这个纯写作请求误编排成了四角色工程小队——**误触发模式的第 4 例现场证据**，已记录。差路由层下，技能编排就是负资产，这句话我们是用自己的产品反复验证的。

## 五、初步结论（标注可信度）

### 5.1 强模型 + 方法论技能：冗余（n=4，高可信）

四轮产物零分离。但过程层有两次真差异：技能组的 AI **主动补失败测试**（调试任务先建反馈环、5 个根因假设、补 3 条测试；网页任务主动写物理自测脚本跑了五遍）——对照组只修不加测。行为被塑形了，产物没被改变。

机制解释（我们称之为 **harness 假说**）：

> **技能 = 提示词层的规范执行；好的 agent harness = 结构层的规范执行；两者并存时，结构层赢。**

强模型在好 harness 里本来就守规矩，技能只是把它已经会做的事再说一遍。

### 5.2 价值矩阵（四格已测三格）

| 场景 | 技能价值 |
|---|---|
| 差路由层 + 技能 | **主动伤害**（5/7 误注入实测） |
| 好 harness + 强模型 + 方法论技能 | **冗余**（四连平手） |
| 好 harness + 弱模型 | **见 5.3——问题问错了** |
| 信息型技能（组织 runbook / 冷门坑 / 项目私有约束） | **唯一存疑价值格，未测** |

### 5.3 弱模型实验：赢的一侧根本没用技能（最重要的意外）

R6 结果表面是碾压：处理组交付 10 文件、2503 行、25 项物理自验全过，得分 22/25（强模型轮是 23.5）；对照组两次尝试**零产物**——纯思考循环到死，一次 88 分钟只做了 2 次工具调用，一次 43 分钟零工具调用。

但机制提取揭示了真相：

- 弱模型路由 **2 次调用全部 no-match**（hook 一次、模型自调一次）；
- 处理组**全程 0 次读取技能文档**（强模型轮同期是 80 次）；
- 模型自己的推理原话："路由没有匹配到技能，任务书本身就是完整的需求文档——直接实现。"

也就是说：处理组赢在**环境脚手架**（协议规则、技能目录的存在、路由 CLI 可用）加上单次实验的运气，而不是技能内容。技能从未进入它的上下文。

由此弱模型格的结论修正为：**"技能能否抬升弱模型"在路由质量解决前是不可检验的问题——弱模型路由本身就是第一瓶颈。** 它连"该用哪个技能"都判不出来，谈何注入效果。

### 5.4 下一步（已重新定向）

1. 弱模型格的下一个实验测**路由质量**（让 27B 路由能正确命中/正确拒判），而不是注入效果；
2. 唯一剩余的可检验价值是**三臂设计**：裸 / 全量技能 dump / 智能路由——护城河只能来自"路由 vs dump"的差值，且只在 50+ 技能规模下才可能显形；
3. 信息型技能格（runbook、私有约束）单独立项——这是矩阵里最后的存疑格。

## 六、给同行的三条元经验

1. **预注册是给自己的护栏。** 六轮里最有用的单一制度。人会向着希望解释数据，预注册文档不会。
2. **验证"处理真的发生了"和验证结果同样重要。** R6 的路由模型静默丢失如果不被三验抓住，我们会发布一个方向完全错误的结论。
3. **负结果要写下来发出去。** 四连平手逼出了 harness 假说、路由审计和重新定向——比任何一次"赢了"的 demo 产生的认知都多。
