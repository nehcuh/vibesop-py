## 0. 先给你们没看到的东西(本次代码抽查新发现)

**triage_service.py:100, 225-255**:LLM triage 的输入不是全量 110 skill,而是 `prefilter_ai_triage_candidates` 用 **KeywordMatcher 预筛的 top-N 窗口**，且 backfill 按**目录原始顺序**补位(:250-253)而非相关度。这意味着：字面层不只是在 LLM **上方**短路——它蹲在 LLM **前面**做召回门。正确 skill 不进窗口，LLM 永远无法挽回。你们方案里“字面层架空语义层”的诊断** understatement 了一半**。

**triage_service.py:216** `self._set_cache(...)`:triage 结果缓存是进程内的，在 CLI-per-invocation 下和熔断器同病——都是服务端假设的死状态。方案修了熔断器却没发现缓存同病，而两者的正确解是同一个：**持久化 query→result 存储**。

**_layers.py:253**:中文按**单字** token 化做 Jaccard。单字重叠在中文上近乎噪声(“提交代码”和“提交PR”共享提/交)。cmspark 流量是中文——**站在 LLM 前面的召回门恰好在流量最重处最弱**。这和你们 task-memory 项目里 BM25 中文 0% 召回是同一个病。

## 1. LLM-first 方向对吗？第三种架构存在，而且已经长在你们代码里

方向半对，框架错了。“级联是为省 $3/月设计的”是个 strawman——级联同时在买延迟、离线能力和(你们没意识到的)候选预筛。用成本论推翻它是对称错误。

真正的架构不是“字面优先 vs LLM优先”的二选一：**系统已经是 retrieve-then-arbitrate,只是 retriever 是坏的**。你们方案 P2 那句“embedding 定位为 triage 的召回器”无意中说出了正确架构，但计划没有跟随自己的推论——把召回器放在最后建。正确顺序:先修召回(embedding 窗口喂给 LLM 仲裁)，再谈谁有短路权威。

两个具体反对：

- **快路径是相关性误差的洗白**。scenario(关键词正则)和 index(单字 Jaccard)是两个同源的字面系统，它们“一致”不是独立印证，是同一类错误的共振。方案刚判定这两层“未校准、不配拥有权威”，转头又让它们的合意获得零成本放行权。"且具体"靠什么定义？margin?Jaccard 分数无校准，margin 又是猜的——**用猜阈值治猜阈值的病**。
- **LLM-default 的账要按秒算，不是按美元算**。$2.77/月无成本，但当前 p50=1000ms 的分布里字面快路径贡献了多少、p99=15.3s 的尾部里 LLM 占多少，**你们现在不知道**——因为 analytics 被 mislabel 污染了(fact 5)。在修好度量之前，方案无法预测自己把 LLM 变成默认路径后 p50 会涨到哪。agent 交互回路里每 turn 都走路由，p50 从 1s 涨到 2-3s 是真实产品成本。

另：70% 流量是上游转发的 `<user_query>`(fact 9),重复率大概率不低——**持久化 query 去重缓存应该放在所有架构讨论之前**，它可能让 LLM 参与率变成例外而非默认，比整个“fast-path vs 仲裁”的设计都便宜。P1 的“短查询历史记忆”是它的残缺版：为什么只记短查询？query→skill 幂等就该全缓存。而且 fact 8 说纠正数据 1903/1903 全 False——历史记忆层**没有任何监督信号可以学习**，冷启动只能喂字面层的决定(垃圾进)或 LLM 的决定(那它就是缓存，直说)。

## 2. 顺序和验收指标的问题

- **P0 把度量和行为变更捆在同一阶段**(mislabel 修正 + scenario 降级)，导致 +10pp 无法归因。且 **+10pp 没有基线**——当前 top-1 在有效集上是未知数(34 条不算)。n=130 的 95% CI 约 ±9pp,+10pp 处在不可测量边缘；eval 集由方案作者自己扩、自己标、自己验收——**自批作业**。正确姿势：先标 130+、让旧系统在新集上跑出基线、再改代码，replay 让这一切免费(见下)。
- **P1 验收“离线 p99 <200ms”指向 P2 才存在的组件**(embedding 降级路径)。若指快路径，正则+Jaccard 今天就 <200ms——门禁要么不可建要么无牙。
- **“反馈非空率 >30%”高估一个数量级**。显式 👍/👎 的行业常态是个位数百分比。30% 只有靠**隐式捕获**才可能：skill 是否被采纳、是否立刻重路由、session 结局如何——这些 hook 全都看得见，免费，而方案只字未提。这个验收会失败，并且连锁拖垮依赖反馈数据做的阈值标定。
- **熔断器持久化+EMA+按因冷却是为服务进程设计的机器装在 CLI 上**。~60 次/天、每次新进程，EMA 跨进程在统计上无意义；真实需求是“激进 timeout + 降级 TTL 标志 + last-good 缓存”，十分之一复杂度。且每个新的跨进程状态文件都是新的 RMW race 面——这个仓库已经被咬过两次(pool.yaml CRITICAL、ReflectionStore)。
- **P2 的 recall@3 其实是第一指标不是最后指标**(见第 0 节：召回门今天就承重)；"p99 不劣化”对本地离线路径轻飘飘满足。
- **全案最大缺失：replay 验证**。1897 条真实日志躺在那里，最便宜的验证是让新级联离线重放全量日志、diff 决策分布——任何阶段都没有它。也没有影子模式上线，行为变更直接凭 130 条手工集进生产。垃圾过滤器没有 FP 率门禁——**过滤器误吃真查询比日志进垃圾更糟**，无界风险无验收。

顺序应该是：度量脊柱(mislabel + eval 基线 + replay harness + 隐式反馈)→ 持久化 query 缓存 + timeout/降级标志 → embedding 召召回替换 KeywordMatcher 预筛(喂 LLM)→ 阈值用累积反馈连续标定(不是某个 phase 的门禁)。

## 3. 哪些事实撑不起赋予它的结论

- **Fact 2 与 Fact 4 内部矛盾**：30% 查询 ≤15 字符 → 约 570 条短查询，scenario 只被“访问”41 次说不通——除非 41 是“命中”不是“访问”(那命中率仅 ~7%,scenario 降级影响 ≤2% 流量，**产不出 +10pp**),或者门控与描述不符。无论哪种，“scenario 降级是 P0 级修复”跑在了数据前面。P0 里真正值钱的是 mislabel 修正。
- **Fact 6 只证明了成本可忽略**，推不出“级联失去存在理由”。它对延迟只字未提，而那才是 LLM-first 的真实账单。
- **Fact 8 反噬短查询记忆层**：零纠正数据 = 无监督信号可学(见上)。“按词数计量”对中文还要引入分词依赖——又一个任意阈值；CJK 按字计本来就比英文按字符计信息密度高，15 字符规则蠢，但词数规则未必更聪明。
- **Fact 1 被 lowball 了**:embedding 不是“不与 LLM 平级竞争”——它(以及它替代的召回层)在 LLM **上游**，今天就在承重，只是用的坏的实现。

## 4. 最大实施风险与被低估成本

1. **自评闭环**：作者定验收、作者扩集、作者标标签、作者验收——整个门禁体系没有外部效度。
2. **交互延迟回归**：按秒计的成本无人建模。
3. **反馈是产品问题不是代码问题**：要 cmspark 出 UI、占用户注意力；隐式信号免费却不在计划里。
4. **每个新状态文件 = 新 race**:熔断器状态、历史记忆、缓存，全是跨进程 RMW;锁与测试的成本没入预算。
5. **没人审计 110 条 skill 描述的质量**：对 LLM 仲裁而言，描述质量就是路由表。仲裁垃圾描述是在给噪声做裁决。

## 5. 留一砍一

**留**:P0 的度量脊柱——mislabel 修正 + 先标注后实现的 eval 基线 + **1897 条日志的 replay harness** + 隐式反馈采集。它是唯一复利、且给其余所有决策去风险的项。

**砍**：熔断器持久化 + EMA + 按因冷却。换成 timeout + 降级 TTL 标志 + last-good 缓存。它是服务时代机器，解决的是每次一进程世界里不存在的问题形态，还自带 race 面。

最后一句：“不选 skill 是一等公民决策”是全案最便宜也最正确的判断，保留。

## 4. 结论摘要

Claude 复审推翻了方案的两个支柱、发现三条新代码证据:

- 新证据1:triage 的候选窗口由 KeywordMatcher 预筛(triage_service.py:225-255),字面层蹲在 LLM 前面做召回门——"架空"诊断 understatement 了一半。
- 新证据2:triage 缓存与熔断器同病(进程内,CLI 下无效),正确解同为持久化 query→result 存储。
- 新证据3:中文按单字 token 化做 Jaccard(_layers.py:253),召回门在流量最重处最弱。
- 推翻"级联=省 $3/月的过早优化"框架:级联同时买延迟/离线/预筛;正确架构是 retrieve-then-arbitrate,retriever 坏了——应先修召回(embedding 窗口),不是 P2 而是主干。
- 快路径(scenario+index 合意放行)是同源字面误差的共振,不是独立印证。
- P0 验收不可归因、+10pp 无基线且在 n=130 的 CI 边缘;反馈 >30% 高估一个数量级,隐式信号免费却未提;熔断器持久化是服务时代机器,应换 timeout+TTL+last-good;全案缺 replay harness(1897 条日志离线重放)。
